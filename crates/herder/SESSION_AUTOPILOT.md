# Семантический автопилот Codex

Владелец Rust оценивает завершённый ход в той сессии, которую включил человек. Для каждого правила он сохраняет собственную ревизию, идентификатор оценённого хода и ключ доставки в существующей базе Herder. Профиль обслуживает несколько правил. Параллельные процессы владельца используют ту же базу и тот же шлюз HumanStop.

## Профиль владельца

Необязательное поле `owner.codex_autopilot` в защищённом профиле Codex задаёт судью и источники персональной политики. Для доставки в существующую сессию нужен общий сокет Codex из `AHAP_CODEX_SOCKET`. Пример использует пути из изолированного стенда.

```json
{
  "state_dir": "/stand",
  "holds": {
    "human_stops": "/stand/human_stops.json",
    "human_requests": "/stand/human_requests.json",
    "choices": "/stand/choices.json",
    "unfinished_sessions": "/stand/unfinished_sessions.json"
  },
  "judge": {
    "base_url": "http://127.0.0.1:8000/v1",
    "model": "fixture-judge"
  }
}
```

Судья принимает OpenAI-совместимый запрос на `chat/completions`. Имя модели и адрес задаёт владелец. Для авторизации можно указать `judge.token_file` с правами `0600`. Клиент принимает HTTPS и локальный HTTP. Необязательное поле `policy_file` указывает путь к общей политике, если UI использует другой каталог.

## Контракт для инспектора и CLI

1. Клиент получает точный `session_ref` через `session.resolve` либо `session.register` и проверяет экземпляр и native ID. В режиме `llm` он передаёт право оценки Rust через существующую запись в `sessions.json`. Запись содержит `harness:"codex"`, `sessionId`, `cwd`, `enabled:true`, `executor:"rust"` и `updatedAt`. С этого момента прежний обработчик Stop уступает сессию Rust. Режим `self`, полные цели Herder и привязки к инцидентам сохраняют своего исполнителя.
2. Для поиска клиент вызывает `automation.list` с этим `session_ref` и выбирает правило `kind:"autopilot"`. Для первого `on` он вызывает `automation.create` с тем же `session_ref`, стабильным `request_key` и `rule:{"kind":"autopilot","instructions":"…"}`. Повтор того же запроса читает существующее правило. При включении владелец запоминает последний завершённый ход.
3. `automation.get` принимает `rule_ref`. Поля ответа включают `session_ref`, `rule`, `revision`, `enabled`, `phase`, `turn_id` и `delivery_task_id`. Поле `enabled` показывает, включено ли само правило. Клиент также учитывает персональный переключатель и HumanStop. Внутренняя оценка хода сохраняет ревизию команд управления.
4. Для `off` клиент сначала выключает персональную запись и вызывает `automation.pause` с `rule_ref` и текущей `revision`. Для повторного `on` он включает персональную запись и вызывает `automation.update` с `rule_ref`, `revision` и `rule`. После `revision_conflict` клиент перечитывает правило.
5. `continue` допускает одну доставку в исходную сессию. При `done`, `human` и `choice` владелец сохраняет решение до нового ввода человека. При незавершённой нативной цели, ожидании ввода, Stop или недоступном судье отправка блокируется. Квитанция доступна через `tasks/get` по `delivery_task_id`, текст ответа — через `session.messages`. После потери подтверждения владелец сверяет исходный ключ с нативным `userMessage.clientId`.

При HTTP 429 инспектор показывает `judge_rate_limited`. Структурированный код нехватки квоты, в том числе Z.AI `1113`, даёт `judge_quota_exhausted`. При потере соединения до ответа статус остаётся `judge_unavailable`. Из ответа провайдера в правило попадает только диагностическая фаза. После перезапуска эти ошибки дают ноль повторных обращений к судье и ноль доставок по этому ходу.

## Проверка

[Пробник CLI](../../tests/native/codex_autopilot_probe.py) вызывает те же MCP-операции. [Стенд](../../tests/native/codex_autopilot_stand.py) создаёт отдельную базу, профиль, сокет и сетевое пространство с одним loopback-интерфейсом. Для воспроизведения из корня worktree передайте путь к исполняемому ELF Codex и собранному владельцу.

```sh
python3 -B tests/native/codex_autopilot_stand.py --codex "$codex_elf" --owner "$herder_owner"
```
