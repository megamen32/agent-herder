# Решение кворума: автопилот до полной цели пользователя

Статус: архитектурное решение после независимых предложений и cross-challenge;
свежая проверка REVISE → две обязательные правки → PASS архитектуры.
Реализация, включение и runtime acceptance не выполнялись.

## Выбор

Развивать существующий semantic autopilot Herder: одна управляемая сессией
цель, сохранённые первичные поручения и уточнения, реестр незакрытых требований,
выбор следующего действия и отдельный аудит завершения по реальным доказательствам.
Не превращать composer predictions в автоматическую бесконечную отправку.
Не создавать новый отдельный judge-сервис или конкурирующий планировщик.

Codex Goals взять как проверенный архитектурный образец persistent objective,
idle continuation, progress/no-progress и completion audit. Подключение самого
native Goals controller **исключено из первого среза**: он активный исполнитель
продолжений, а не пассивный транспорт. Одновременные native Goals и Herder
continuation для одной сессии запрещены. Возможный будущий native режим требует
доказанной исключительной передачи управления, общей остановки и учёта квоты.

## Почему это отвечает именно пользовательской цели

Цель хранится полным исходным текстом со ссылками на материалы, а не заменяется
кратким business KPI, очередным промптом или модельным summary. Автопилот следует
тому, чего хотел пользователь, включая изменения направления, ограничения,
ожидаемую форму результата и требуемую проверку. Для некоммерческих задач это
может быть понятное объяснение, работающий интерфейс, исследование или личный
результат; единого бизнес-показателя здесь нет.

Реестр требований — производное представление, а не новый источник истины.
Каждое требование ссылается на первичный запрос/уточнение; модель не может
молча удалить его или объявить заменённым. Неоднозначная реплика не отменяет
старое поручение. Сообщения агентов и цитируемые инструкции сами по себе не
создают новых полномочий владельца. Если неоднозначность меняет цель и мешает
безопасному действию, нужен один точный вопрос; совместимая работа продолжается.

## Работа одной сессии

1. Пользователь явно включает автопилот для текущей задачи. Он видит, к какой
   цели привязан режим; глобальная автоматика и старые завершённые поручения
   от этого не оживают. Нужен явный выбор действующего поручения, а не захват
   всей исторической переписки как незакрытого backlog.
2. Сохраняются точная native session identity, исходные пользовательские события,
   версия цели, действующие ограничения и критерии успеха. Новое авторитетное
   уточнение создаёт следующую ревизию; предыдущая остаётся прослеживаемой.
3. После завершения хода существующий controller проверяет native idle,
   пользовательский ввод, pending approval/question и текущую остановку. Затем
   определяет полезное следующее действие по цели, оставшимся требованиям и
   изменившимся доказательствам. Не создаётся новый ход поверх активного.
4. Одно ограниченное продолжение доставляется существующим штатным путём.
   Перед отправкой повторно проверяются goal revision, native identity и свежие
   полномочия. Accepted/UNKNOWN квитанции сохраняются и не переотправляются.
5. Если исполнитель считает работу законченной, отдельный аудит получает
   первичные поручения и актуальную ревизию, сверяет полноту реестра и требует
   подтверждения результата по каждому активному требованию. Слова ассистента
   «сделано», HTTP200 или закрытая карточка сами по себе достаточность не доказывают.
6. Неподтверждённый пункт остаётся открытым. Блокер, ожидание процесса и лимит
   бюджета — отдельные состояния, не success. Новое сообщение пользователя
   инвалидирует старое решение о завершении ещё до его применения.

Проверка должна соответствовать задаче и уже выданным полномочиям: результат
интерфейса проверяется на пользовательском пути, внешний эффект — по квитанции
и readback, исследование — по покрытию вопросов и источникам. Автопилот не
создаёт новые проверки/звонки/покупки/внешние действия вне разрешённой области.
Если критерий требует именно оценки человека, она не подменяется самооценкой ИИ.

## Как расходовать больше Codex с пользой

Сильную Codex-модель использовать для контроля сложной цели, разбирательства
противоречий и строгой проверки кандидата на завершение. Частоту дорогих
проверок задаёт существенное событие: новая цель/уточнение, спорный прогресс,
предложение завершить или повторение цикла. Нет причины отправлять полный
исторический чат второй модели после каждого tool call или таймера.

Рабочая сессия продолжает использовать свой выбранный проектом маршрут.
Контрольная модель и исполнитель — отдельные роли; изменение одного не
означает скрытого переключения другого. Нативная Codex-подписка не заменяется
платным API ради удобства реализации или кеша. Контрольный Codex-путь нужно
реализовать через существующий поддерживаемый adapter/auth; совместимость
нынешнего OpenAI-compatible judge с ним пока не доказана.

## Четыре разных средства экономии

1. **Повторная обработка:** Stop и периодический semantic path должны сходиться
   к одному решению для exact session + goal revision + turn/evidence version.
   Уже оценённый неизменившийся снимок повторного модельного вызова не требует.
2. **Рабочий контекст:** цель и действующие требования сохраняются целиком;
   в обычную оценку добавляются изменения и адресуемые evidence. Перед final
   audit доступны полные исходные поручения. Сжатие — не кеширование и не
   даёт права забыть ограничение.
3. **Provider KV/prompt cache:** стабильный префикс, одинаковый модельный маршрут,
   фиксированные инструкции и append-only история внутри ревизии. После
   compaction/смены цели/модели кеш может стать холодным. API cache options
   применимы только при подтверждённой поддержке фактического transport/provider.
   API скидки нельзя обещать для Codex subscription. Hit/cost пока неизвестны.
4. **Извлечение данных:** переиспользовать разобранный неизменившийся transcript
   по native cursor/fingerprint; не устраивать новые полные обходы SQLite/FTS.
   Любая разрешающая проверка и существенный внешний факт читаются заново
   перед действием, даже если semantic решение было взято из memo.

Измерять следует provider input/output/cached-input tokens, число вызовов
судьи на полезный шаг, задержку до результата и ошибки завершения. Проценты
экономии и оптимальные размеры контекста сейчас не измерены и не заявляются.

## Сравнение альтернатив

| Вариант | Полная цель и разные среды | Цена/сложность | Почему выбран/отложен |
|---|---|---|---|
| Автоотправлять predictions | Не удерживает обязательства и доказательство завершения | Малый объём кода; риск лишних ходов | Не соответствует задаче |
| Native Codex Goals как единственный controller | Уже силён для Codex; cross-harness contract и full-proof export неизвестны | Меньше своего цикла для Codex; интеграционный риск | Самостоятельный будущий режим после проверки exclusive ownership |
| Развить Herder | Есть cross-harness control, guards и receipts; нужно исправить goal/evidence representation | Средний продуктовый объём; стоимость модели ещё неизвестна | Выбор для текущего продукта |
| Новый отдельный evaluator-сервис | Сам по себе не создаёт отсутствующие требования/доказательства | Дополнительный runtime/state/операции | Не нужен на первом срезе; evaluator может быть модулем Herder |

## Что изменил настоящий cross-challenge

Первоначально оба участника допускали native Goals как транспорт. После критики
эта формулировка снята: нужен один владелец продолжения. Также снята идея, что
ledger + отдельный LLM verifier сами по себе гарантируют полноту: extractor и
verifier способны согласованно потерять один смысл. Поэтому финальный аудит
сверяет реестр с первичными поручениями, а само evidence оценивается по задаче.

Существенный остаточный риск — неверное понимание неявного намерения пользователя.
Независимая модель снижает отдельные ошибки, но не даёт математической гарантии;
проверяемые внешние факты и понятная человеку активная цель обязательны.

## Обязательный контракт применения решения после независимой проверки

Завершение — защищённый переход состояния, а не просто текст судьи. Аудит
привязан к native identity, goal revision, cursor всех принятых пользовательских
событий, evidence version и stop/control epoch. Controller атомарно применяет
completed только при совпадении этих значений и отсутствии принятого, но ещё
не обработанного пользовательского ввода. Одна goal revision недостаточна:
уточнение может уже сохраниться, но ещё не попасть в её производную проекцию.
Несовпадение отменяет применение старого решения; stop/выключение также
отменяют подготовленную отправку. После рестарта действует тот же барьер,
старый аудит не может закрыть новую работу. Конкретный механизм сериализации
нужно доказать при реализации; здесь зафиксирован обязательный контракт.

Cached done не обходит этот барьер. Каждое существенное доказательство имеет
происхождение, наблюдаемую версию или срок актуальности и связь с требованием.
Изменение/истечение доказательства, отзыв полномочий либо недоступность
существенного первичного материала инвалидируют применимость memo даже при
неизменном чате. Аудит действительно получает или читает полные существенные
первичные материалы: одна ссылка без доступа и молчаливое усечение запрещают
done. UNKNOWN внешнего эффекта не является ни успехом, ни разрешением повтора.

Минимальные будущие проверки: задержанный audit против принятого уточнения,
stop и рестарта; неизменный transcript против отозванных полномочий, изменённого
внешнего результата и недоступного вложения. Старое решение не отправляет шаг
и не закрывает цель, новое событие обрабатывается ровно один раз. Эти проверки
в исследовании не выполнялись.

## Минимальный будущий срез и способы опровергнуть решение

Одна явно включённая сессия, существующий controller, оригинал цели + ревизии,
одна передача шага, полный coverage audit на candidate done. Native Goals,
новый scheduler/service, автоматическое расширение других сессий не входят.

Решение нельзя считать пригодным, если: длинный первый запрос или поздняя
поправка исчезают из цели; маленький промежуточный результат закрывает всю
задачу; новая человеческая реплика не отменяет старое решение; memo допускает
действие после отзыва разрешения; один accepted input порождает повтор; после
рестарта появляется второй controller; бюджет/живое ожидание объявляются done.
Будущий проверочный набор должен содержать эти случаи и независимую оценку
пользовательского результата. В этом исследовании набор не запускался.

## Модели и границы вывода

Независимые предложения: gpt-6.1-sol и gpt-6-luna через native collaboration,
затем по одному cross-challenge. Это две реальные модели одного провайдера;
межпровайдерное согласие не заявляется. Sol после критики вернул REVISE;
Luna сохранила выбор условно. Итог учитывает оба замечания, а не голосование.
Архитектура выбрана, её превосходство на бизнес-корпусе ещё не измерено.
