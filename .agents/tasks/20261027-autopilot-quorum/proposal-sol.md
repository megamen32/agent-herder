# Независимое предложение Sol

Модель: gpt-6.1-sol. Основание: общий report.md; дополнительные проверки runtime, модельные запросы и тесты не выполнялись. Стоимость, задержки и процент попаданий в prompt cache не измерены.

## Выбор

Эволюция существующего Herder: небольшой версионируемый реестр полной цели плюс отдельная проверка завершения. Native Goals использовать как механизм продолжения Codex, если интерфейс доступен, но не как второй независимый источник требований. Не создавать отдельный сервис semantic judge на первом срезе.

Цель — сессия выполняет всё действующее поручение, включая последние уточнения, и заканчивает только при проверяемом покрытии обязательств либо честно останавливается с точным незавершённым остатком. Нельзя гарантировать достижение цели при отсутствующих полномочиях, ресурсах или ответе человека; можно гарантировать отсутствие ложного done и продолжение разрешённой работы.

## Три жизнеспособных пути

| Архитектура | Сильная сторона | Ограничение и опровержение выбора |
|---|---|---|
| A. Развитие Herder | Сохраняет guards, receipts, exact-native snapshots и все harness; исправляет конкретный пробел goal coverage | Требует доступа к полной последовательности пользовательских изменений. Опровергается, если текущие события/хранилище принципиально не позволяют атомарно связать revision и отправку продолжения без переписывания supervisor |
| B. Native Goals + cross-harness adapter | Codex сам продолжает thread и учитывает бюджет; меньше внешних толчков | Для других harness семантика неодинакова; возникает риск двух контроллеров. Опровергается как основной путь, если свежая поправка или HumanStop допускает лишнее продолжение либо completion не даёт полного coverage. Выбирать вместо A, если native интерфейс уже надёжно предоставляет эти гарантии и экспорт доказательств |
| C. Отдельный semantic judge с собственным API/хранилищем | Независимость от harness, сильная модель может глубже оценить результат | Новый сервис не создаёт отсутствующих доказательств; добавляет рассинхронизацию и эксплуатацию. Опровергается, если ошибки объясняются неполным evidence, а отдельность не улучшает слепую проверку при одинаковом входе. Оправдан позднее при нескольких независимых потребителях |

Для всех вариантов цена и latency unknown. Сравнивать надо стоимость принятой завершённой задачи и ложные done, а не стоимость одного verdict.

## Контракт цели

Один durable ledger на native session: исходный пользовательский текст со ссылкой на событие; упорядоченные изменения; текущая revision; обязательства с источником, критерием результата, границами и состоянием; ссылки на доказательства. Полный исходный текст хранить, компактное представление можно восстановить. Ledger — не новый roadmap и не самостоятельно расширенный бизнес-план.

Уточнение по умолчанию изменяет только явно затронутые обязательства. Замена/отмена цели требует явного указания или сильного контекстного основания; неоднозначность сохраняет исходное поручение и выделяет вопрос. Вопрос о статусе не заменяет задачу. Semantic extractor предлагает изменение с цитатами; отсутствие цитаты запрещает тихое удаление требования. Не требовать подтверждения каждого extraction; спрашивать только при существенной развилке смысла.

Пользовательский event increment revision немедленно. Verdict и continuation содержат revision и native snapshot. Перед отправкой проверяются оба; устаревший verdict отклоняется. При queued user input автоматическое продолжение не отправляется. Native Goal получает ссылку/проекцию той же revision. У Codex ровно один владелец continuation: native lifecycle либо Herder, никогда оба.

## Планирование и приёмка

Исполнитель/planner выбирает следующий разрешённый шаг. Verifier получает все действующие обязательства, изменения с прошлого решения, доказательства и ссылки на первичные артефакты. Он не переписывает цель и не придумывает пользователю новый запрос.

Done требует coverage каждого обязательства: evidence соответствует точному критерию и реальному consumer path, либо пользователь явно отменил требование. Commit, тест и deployment не взаимозаменяемы. Одного JSON verdict недостаточно. Структурная проверка ловит пропуски, сильный Codex оценивает смысл и противоречия; независимость роли не равна доказанной независимости ошибки. Недоступное доказательство означает incomplete/needs-evidence.

Сильный Codex нужен для неоднозначного изменения цели, существенного перепланирования и финального semantic acceptance. Рутинные lifecycle guards, дедупликация и обнаружение изменений выполняются кодом. На обычном idle достаточно компактного решения по изменившимся обязательствам; не вызывать полный verifier после каждого tool call.

Semantic memory помогает находить прежние решения, но не заменяет ledger. Decision memo хранит проверенные решения с revision, evidence IDs и условиями инвалидирования. Provider KV cache экономит повторение стабильного префикса, но не является памятью/полнотой: сохранять cached-token accounting, держать стабильные инструкции и исходную цель впереди, динамический delta позади. Не обещать экономию без измерений.

## Долгие задачи и остановки

Continuation включается пользователем для конкретной сессии, с видимыми budget и stop; глобальный default не меняется. HumanStop, permissions и pending input приоритетнее автопилота. Accepted/UNKNOWN действия не повторяются: сначала readback receipt, при невозможности — точный блокер.

Verified wait содержит конкретный внешний job/resource, receipt, условие пробуждения и срок следующей проверки. Он не означает ждать чужой milestone. Повтор шага без нового evidence не считается прогрессом. При no-progress сначала один ограниченный пересмотр гипотезы; далее остановка с остатком и причиной. Исчерпание бюджета — не completed; checkpoint сохраняет ledger, receipts и безопасный следующий шаг. Новые бюджеты и разрешения не выводятся из желательности результата.

## Минимальный вертикальный срез

Одна сессия Codex, существующий Herder, opt-in и ledger; без нового сервиса и универсального planner. Сценарий: исходная цель из трёх обязательств, позднее уточнение одного, compaction, незавершённый consumer proof и UNKNOWN мутация. Ожидается сохранение всех действующих обязательств, отклонение устаревшего done, отсутствие replay, остановка budget/HumanStop и продолжение после разрешённого resume. Затем один реальный изолированный consumer результат с полным coverage. Измерить input/output/cached tokens, задержки и ручную оценку ложных done. Если evidence недоступен через существующий snapshot, сначала исправить его доставку, не усиливать модель вслепую.

Главная слабость выбора: реестр тоже строится моделью и способен ошибочно истолковать изменение цели. Сохранённые первичные события, запрет тихого удаления и отдельная финальная сверка уменьшают риск, но не устраняют его; это главный предмет следующего adversarial challenge.
