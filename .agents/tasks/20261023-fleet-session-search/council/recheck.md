## Supported

Синтез технически существенно лучше реестра намерений: CAS, ссылки и GC принадлежат реальному владельцу мутации. Правильны отказ от regex enforcement, обязательного worktree для каждой сессии, heartbeat, автоматических LLM-переговоров и глобальной очереди релизов; монотонная revision вместо payload-hash; сохранение UNKNOWN pins; запрет lease-based takeover без fencing/остановки старого исполнителя. Source worktree и runtime isolation правильно разделены. Существование всех этих guards в production НЕ доказано.

Нормальные чтение, поиск, сборка immutable кандидата, unit tests и тесты в собственных временных каталогах могут идти сразу, без нового API/hook/heartbeat/LLM. Исключение — тест реально пишет в общий runtime/config/DB/порт: тогда нужен именно его существующий seam или отдельное окружение, а не общий запрет на tests. Shared checkout допустим при непересекающихся owned paths; при source collision — настоящий Git worktree, без stash/reset/временного overwrite чужого файла.

## Required corrections before implementation

1. **Закрыть окно GC, не только проверку ссылок.** Контрпример: GC под lock выбирает B без ссылок, отпускает lock; activate B корректно проходит CAS; GC удаляет B по сохранённому списку. Итог dangling несмотря на исправный CAS. Синтез подразумевает общий домен, но должен явно запретить разрыв между финальным ref-check и исключением нового ref-writer. Минимум для малых каталогов — check+unlink в той же секции. Для медленного удаления — durable tombstone/rename в недоступное новым refs пространство под guard, затем unlink вне него; admission и finalize обязаны отвергать tombstone. Не требуется новый GC framework. Ещё дешевле временно не запускать автоматический GC именно управляемых кандидатов; не отключать чужую уборку всего хоста.
2. **Определить protected commit, не сериализовать весь релиз.** Build/hash/тесты/подготовка manifest вне lock. Под lock — перечитать revision, проверить admitted artifact/config, durable intent/in-flight + pin, сделать короткий pointer/ref transition либо tombstone. Restart/readback вне filesystem lock. Пока transition не завершён, второй promote той же installation получает conflict/busy с operation_id, а не ждёт в очереди. Durable in-flight всё равно сериализует consequential transition одной installation; обещать параллельные переключения тех же трёх units нельзя. Разные установки продолжаются независимо, кроме короткого общего ref-store commit при действительно общем artifact store.
3. **Config CAS сам по себе недостаточен.** Проверили config R4; другой writer пишет R5; activate binaries для R4 проходит installation-CAS. Отдельные успешные CAS не дают общей атомарности. Предпочесть уже поддерживаемый immutable versioned config pointer или единый короткий commit. Если seam отсутствует, первый guard scope исключает coupled config mutation; честно исключить конкурентных config-writers из гарантии. Не строить универсальный merge/store. Не навязывать точную config revision всем релизам: manifest может разрешать совместимый диапазон/schema.
4. **Recovery и idempotency должны быть специфицированы до обещания.** Сначала lookup operation_id, затем revision-check; иначе успешный retry после роста revision ошибочно конфликтует вместо возврата receipt. ID связан с canonical arguments; другой payload с тем же ID отклоняется. Crash после эффекта до receipt требует наблюдения/идемпотентного продолжения, а не объявления exactly-once. Durable journal включает необходимые fsync/rename/recovery ordering, если заявляется crash durability; JSON write не доказательство. Expiry не снимает pins; persistent UNKNOWN блокирует только новые consequential mutations своей установки, а не диагностику/сборку. Недоступный журнал, reused ID и прямой same-UID write остаются явными границами.
5. **Семантический merge не превращать в ритуал.** Новый candidate не обязан механически происходить от каждого deployed SHA: cherry-pick/backport допустимы. Нельзя просто обновить expected_revision и стереть чужое поведение. Проверить актуальные desired source/provenance и затронутые regression checks; ancestry — дешёвый сигнал, не доказательство. При отсутствии source provenance нужен адресный вопрос владельцу спорного поведения, а не полный council/всеобщий re-review.

## Measured checks and limits

Команда: `python3 council/experiments/recheck_fixture.py` из каталога задачи. Скрипт и `recheck-results.json` сохранены. PROTOTYPE; Git создавался только внутри TemporaryDirectory и удалён при выходе.

- **Реальный Git fixture:** staged и unstaged версии одного tracked файла, untracked binary и index entries побайтно/структурно совпали до и после отдельного worktree, изменения и commit в нём. Изолированный owned commit существует; исходный WIP не изменился. Это доказывает конкретный inspect-act результат, не запрет same-UID обхода и не будущую интеграцию.
- **Детерминированная GC schedule:** valid activation-CAS + delayed unlink дали dangling. Исправленная модель с tombstone отвергла admission; A→B→A сохранило hash и отклонило старую revision. Это контрпример и модель контракта, не production race/load/durability test.
- **Config schedule:** отдельная проверка R4, конкурентный R5, затем activation воспроизвели несовместимый результат. Production config writers не исследованы.
- **Bounded source observation:** существующий `scripts/coordination-hook.mjs` уже отправляет `/api/coordination/activity`, читает `/api/coordination/context`, содержит regex path/write inference и fail-open catch. Это supported seam отображения/контекста, не executor fencing или release ownership. Поэтому новый mandatory hook/context packet не обоснован. Release-controller storage/GC seam этим просмотром НЕ установлен.

Runtime latency, crash recovery, retained receipts, production writer coverage и потребительская приёмка не измерены. Время toy fixture не используется как latency budget.

## Minimum final protocol and ownership

Оставить Astra с уточнениями выше: Git worktree по source collision; existing release controller с expected monotonic revision, operation receipt/in-flight, refs/pins и общей GC exclusion; config coupling только в реально поддержанном seam. Сборки/чтение/обычные tests свободны. При conflict читать существующую receipt, интегрировать изменения, пересобрать только затронутое; при UNKNOWN сверять ту же операцию. Herder по запросу показывает resource/owner/receipt, без второго truth store, обязательных рассылок и heartbeat.

Следующий bounded исполнитель controller владеет только конкретными существующими activate/rollback/finalize/GC adapters и их tests после source map всех писателей. Он сначала доказывает реальные пути, не реализует четыре новых публичных API по названиям Astra. LHC worker владеет кратким правилом source/runtime conflict. Herder UI worker нужен только если текущая карточка не может показать уже существующую receipt: иначе никаких UI изменений. OS permission migration, universal registry, regex hooks и новый scheduler исключены. Реальные release/GC/config edits требуют отдельного уже назначенного ownership scope; этот recheck их не совершал.

**Verdict:** направление SUPPORTED, текст REVISE указанными точными условиями; implementation guards и production acceptance — NOT CLAIMED. Нет основания повторять совет или расширять платформу: привязать минимальный контракт к действительному controller и проверить его конкретные bypass paths.

## Delta recheck: ACCEPT with limitations

Перечитаны только исправленные `astra-synthesis.md` и `final-decision.md`; повторные tests не запускались, новой причины нет. Пять узких исправлений внесены по существу: GC ref-check связан с unlink либо tombstone запрещает новые refs; два отдельных config/installation CAS прямо признаны недостаточными; operation ID и digest канонических аргументов проверяются до revision; UNKNOWN требует readback той же операции; короткий commit guard отделён от restart/readback, конфликтующий promote получает немедленный busy/conflict. Same-UID bypass и отсутствие production proof сохранены явно. Нет обязательных regex hooks, global claims, heartbeat, формального ancestry gate или очереди на весь release/build цикл.

Это ограничения честного обещания, не требование нового совета, повторной авторизации обычной работы или дополнительных ритуалов.
