# Синтез Astra: параллельная подготовка, защищённая смена общей установки

Статус: предложение для независимой перепроверки, не production-гарантия и не разрешение менять другие проекты. Автор назначен как `gpt-6-astra`; это назначение, отдельной provider-квитанции здесь нет. Прочитаны полные `sol-proposal.md`, `minimax-proposal.md` и `minimax-brief.txt`, применимые AGENTS, LHC council/challenge-decision. MiniMax-ответ имеет native receipt `turn_314d18c1-b60c-4a98-a189-9e29bc85e9e1`, actual model `MiniMax-M3.1-Flash`; Sol остаётся отдельным предложением. AgentMemory ответил, но вернул нерелевантные исторические записи: они не используются как факты проекта. Репозиторий и production повторно не исследованы; эксперименты ниже предложены, не выполнены.

## Суть решения

- При конфликте исходников продолжать в настоящем Git worktree, переносить только собственное; чужой checkout, WIP и историю не трогать.
- Защищать одну конкретную installation в её существующем release controller: монотонная revision, журнал операции, проверка фактического состояния.
- В том же контуре защищать ссылки на артефакты и GC. Worktree не защищает runtime, конфигурацию или удаление кандидатов.
- Не создавать глобальный реестр claims. Herder показывает владельца операции и её receipt из controller; LHC задаёт маршрут работы и реагирует на конфликт.
- Устаревший кандидат нельзя сделать безопасным, просто перечитав revision: требуется интеграция исходников и проверка сохранения чужого результата.
- UNKNOWN блокирует новые изменения только затронутой установки; сборки, тесты и независимые установки продолжают работать.
- Нормальный проход обходится без LLM-переговоров, heartbeat сессий, review каждой команды и рассылки контекста.
- Прямую запись тем же UID этот протокол не запрещает. Полная защита требует отдельной границы прав и миграции всех писателей.

## Почему именно это

По brief, другая явная activation в 20:11 вернула три Linux-сервиса на `68bf`, удалены наши кандидаты `380/0a`, `current` остался dangling на `0a`. CAS остановил наше повторное переключение. Точный исполнитель и автоматический реконсайлер не установлены; поздние owner-notes не доказывают прежнего знания о владении. Следовательно, искать виновника по догадке или добавлять обязательное объявление намерений недостаточно. Подтверждённая дыра — общая мутация и удаление зависимостей не составляли один проверяемый контракт.

Выбираю основу Sol: локальный владелец мутации. Из MiniMax сохраняю разделение source/runtime/config/GC, но отвергаю обязательный worktree каждой сессии, универсальную строку реестра, heartbeat и path-claims как первый релиз. Видимый claim не обеспечивает запрета файловой записи; отдельные units каждой сессии полезны для тестов, но не заменяют безопасное переключение общей установки. Новая инфраструктура нужна только там, где конкретный эксперимент покажет недостаточность существующего controller.

| Альтернатива | Польза | Сложность и задержка | Риск / критерий отказа |
| --- | --- | --- | --- |
| Инструкция + worktree + CAS указателя | Быстро защищает исходники при кооперативной работе | Низкая; численная latency неизвестна | Не закрывает GC, ABA, partial; dangling в гонке опровергает достаточность |
| Существующий controller: revision + журнал + pins | Закрывает наблюдаемую гонку в маршрутах, которые действительно проходят controller | Средняя; добавляет локальную транзакцию и readback, latency неизвестна | Любой обходящий GC/activate или устаревший семантически кандидат разрушает обещание |
| Реестр сессий/claims/leases и отдельный runtime каждой сессии | Полезен при массовом управлении временными окружениями | Высокая; heartbeat, восстановление реестра, дополнительный отказ; latency неизвестна | Не решает доступ того же UID; если второй вариант проходит проверки, эта сложность пока избыточна |

## Минимальный контракт и точные места проверки

Названия ниже — предлагаемый интерфейс, не утверждение о существующих API. Первый исполнитель должен привязать их к реальным функциям activate, rollback, candidate-finalize и GC. Если текущий controller уже хранит нужное состояние, расширяется его запись; второй store запрещён без доказанной необходимости.

`read_installation(resource_id)` возвращает монотонную revision, desired/observed payload identity, связанную config revision, текущую незавершённую operation. Revision увеличивается при каждом принятом переходе, включая возвращение к старому payload: A→B→A не возвращает прежнюю revision. Фактические unit/process/import identities проверяются отдельно от симлинка. При расхождении с журналом controller возвращает drift и не выполняет новый переход по старой модели мира.

`finalize_candidate(digest, manifest, operation_id)` атомарно публикует immutable payload и durable pin до того, как GC получает право его рассматривать. Сборка идёт в приватном staging, который этот GC не обслуживает. Manifest содержит исходный commit/tree, build inputs, проверки и config-совместимость; digest бинарника не заменяет provenance. Pin снимается после однозначного завершения/отказа владельца либо согласованной recovery, а не после пропущенного heartbeat. Это запись артефакта/операции, не обязательная регистрация всей сессии.

`activate(operation_id, expected_revision, candidate_digest, config_requirement)` сначала ищет operation_id и сравнивает digest канонических аргументов: совпадение возвращает сохранённую receipt или UNKNOWN для readback, несовпадение отклоняется. Только новая операция проверяет revision, фактическое состояние, pins и совместимость. Иначе успешный retry ошибочно конфликтовал бы с уже увеличенной revision. Журнал намерения сохраняется до первого эффекта; повтор UNKNOWN не означает повтор мутации. Технический rollback проходит тот же контракт и не используется для устранения конфликта с чужой работой. Для этой задачи нет разрешения откатывать чужой runtime.

Минимальная запись операции: resource_id, operation_id, expected revision, target digest, owner session/task reference, фаза, наблюдаемые identities и terminal receipt. Owner-reference нужен для адресного вопроса, а не как самостоятельная блокировка. Часы и диагностические timestamps полезны, но не определяют право на мутацию.

Для трёх services нельзя обещать атомарность filesystem-rename. Контроллер ведёт фазы и вектор наблюдаемого состояния компонентов. Build/hash/tests и подготовка manifest вне lock. Под коротким lock — повторная проверка revision/artifact/config, durable intent/in-flight и pins, короткий pointer/ref transition. Restart/readback вне lock; durable in-flight исключает следующую activation этой установки, возвращая busy/conflict с operation_id без очереди. Разные установки независимы, кроме короткого commit общего ref-store. Если асинхронный старый исполнитель способен продолжить после takeover, fencing проверяется непосредственно исполнителем каждого эффекта; иначе takeover запрещён до доказанной остановки старого исполнителя. Lease сам такого доказательства не даёт.

`gc()` в общей секции с ref-writers перечитывает ссылки: активные desired/observed payloads, in-flight/unknown, pinned candidates и recovery payload. Между финальным ref-check и исключением нового ref нельзя отпускать guard. Для малого удаления check+unlink выполняются внутри; для медленного — durable tombstone/rename под guard, unlink снаружи, finalize/admission отвергают tombstone. Shared store требует согласования всех его ref-writers; lock одной установки недостаточен. Самый простой допустимый MVP — не удалять автоматически именно управляемые кандидаты до проверенного GC, сохраняя чужую уборку. Нехватка диска останавливает новые сборки, а не разрешает удаление по возрасту.

Конфигурация сохраняет существующий store. Независимые config-CAS и installation-CAS недостаточны: между ними может появиться несовместимая config. Нужен уже поддерживаемый immutable versioned config pointer или единый короткий commit с writers. Manifest задаёт точную revision лишь при необходимости, иначе совместимый диапазон/schema. Если seam отсутствует, MVP исключает coupled config mutation и конкурентных config-writers из гарантии. Новый универсальный config-канон и обязательный review настроек не нужны.

## Source и семантика релиза

При чужом WIP пересекающиеся изменения делаются в новом Git worktree от известной основы. Переносятся только атрибутируемые собственные commits/patches; смешанный файл целиком не копируется. Отдельные ветки нужны этому worktree, но не навязываются независимой работе в чисто разделённых путях. Git не запрещает процессу того же UID зайти в чужой каталог; это дисциплина плюс изоляция путей, не security boundary.

Отказ CAS означает: текущая установка изменилась, прежний release plan больше не применим. Исполнитель читает receipt и актуальные desired source/provenance, интегрирует своё в своём дереве, пересобирает и выполняет затронутые regression checks. Просто обновлять expected_revision старого кандидата запрещено. Ancestry — дешёвый сигнал, не доказательство; cherry-pick/backport допустимы без механического включения каждого deployed SHA. Проверяются сохранение затронутого чужого поведения и своё изменение. При отсутствующей provenance нужен адресный вопрос владельцу спорного поведения, не новый council; блокируется этот promote, подготовка продолжается.

Herder получает данные по запросу и показывает ровно конфликт, owner-reference и ссылку на receipt в существующей карточке. LHC учит одному маршруту: source conflict → worktree; runtime conflict → readback и интеграция; unknown → reconciliation того же operation_id. Успешная работа молчит. Сообщение соседу нужно только когда его решение или передача ресурса меняет следующий шаг.

## Сбои и границы обещания

Crash после эффекта до receipt приводит к reconciliation фактических identities, не к слепому повтору и не к обещанию exactly-once. Частичный результат остаётся partial; только доказанно идемпотентный оставшийся шаг можно продолжить. Crash durability требует проверенного fsync/rename/recovery ordering, не просто JSON write. Недоступный журнал блокирует новую consequential mutation установки, но не диагностику/сборку. UNKNOWN сохраняет pins; expiry не разрешает удаление, повтор или takeover. Ошибка документации не отключает машинную проверку.

Legacy-клиент без revision не допускается к защищённой мутации; reads/builds остаются доступны. До миграции всех activate/rollback/GC/config-путей обещание ограничено перечисленными маршрутами. Ручная запись тем же UID может обойти guard: readback обнаружит drift позднее, но не предотвратит потерю. Идеальная последующая граница — controller под отдельными правами, недоступный агентам writable store и единственный API мутации. Это отдельная задача прав/эксплуатации, не скрытый шаг этого плана.

## Пять различающих экспериментов

1. **Source + семантика.** В disposable Git fixture чужой dirty-файл и чужая опубликованная функция; второй участник делает своё в worktree. Проверить байтовую неизменность чужого WIP и обе функции после интеграции. Подсунуть кандидат с новой revision, но старым содержимым: принятие опровергает release-contract.
2. **Activation + GC + ABA.** Два кандидата от R и конкурентный GC; один activate проходит, второй получает conflict, оба referenced payload сохраняются, unreferenced удаляется. После A→B→A старый R отклоняется. Dangling, два принятых R или удалённый pin — falsifier.
3. **Crash-window.** Убить fixture-controller до эффекта, после первого из трёх шагов и после эффекта до receipt. Читать тот же operation_id; новый release не принимается до reconciliation. Повтор неидемпотентного эффекта или непомеченный partial опровергает recovery.
4. **Expiry и обход.** Истёкший lease при живом исполнителе не снимает pin и не разрешает takeover; legacy-запрос отклоняется. Прямой same-UID write намеренно проходит вне API и затем обнаруживается как drift: если отчёт называет его предотвращённым, гарантия ложна.
5. **Цена нормального прохода.** Сравнить два независимых builds и две разные installations до/после guard: wall time, p50/p95 mutation latency, число LLM/tool coordination calls. Ожидается ноль новых LLM-раундов и отсутствие взаимного ожидания разных installations. Численные бюджеты устанавливать по baseline, не выдумывать заранее.

Все fixtures изолированы, без production mutations, звонков и уведомлений владельцу. Они не доказывают покрытие реальных путей, устойчивость production-хранилища при потере питания, безопасность OS-прав и совместимость настоящих сервисов.

## Поправки после независимой проверки

`recheck.md` дал REVISE narrowly; изменения выше закрывают его пять замечаний. По `council/experiments/recheck-results.json` реальный временный Git worktree сохранил staged/unstaged/untracked/index исходного дерева; модель valid CAS + delayed GC unlink воспроизвела dangling, tombstone-модель отвергла admission, ABA отвергнут revision; отдельный config precheck воспроизвёл несовместимость. Это выполненные проверяющим prototype-проверки, здесь повторно не запускались. Их 150.98 ms — не runtime latency. Production controller, writer coverage, crash durability и consumer acceptance не доказаны. Нормальные reads/build/tests не получают нового ритуала; tests с записью в общий runtime/config/DB требуют его seam или отдельной fixture. Существующий coordination-hook — только контекст/отображение, не основание добавлять новый обязательный hook. Финальный краткий контракт — `final-decision.md`.

## План для назначения исполнителей

1. **Владелец текущего release controller:** read-only карта конкретных activate/GC/config писателей и существующих receipt/storage seams; результат — точные файлы и подтверждённые обходы. При готовом контракте исправлять обход, не создавать новый controller.
2. **Один Worker controller:** только установленные на шаге 1 adapter/journal/GC пути и изолированные tests; реализовать минимальный revision/in-flight/pin контракт и эксперименты 2–4. Не менять продуктовый runtime или права.
3. **Worker LHC, после выбора API:** только релевантная инструкция source/release conflict и fixture 1; никаких shell-regex hooks и глобальных claims. **Worker Herder:** только отображение существующей operation/receipt по запросу, если текущего отображения недостаточно.
4. **Независимый проверяющий:** оспорить этот синтез до реализации, затем проверить конкретный diff и эксперимент 5. Отдельный последующий этап — миграция production-маршрутов и consumer acceptance по согласованному scope. Здесь они не выполнены и не объявлены разрешёнными.
