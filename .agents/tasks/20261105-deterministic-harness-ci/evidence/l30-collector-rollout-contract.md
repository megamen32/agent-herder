# L30: подключение post-deploy collector

Основание: `evidence/l20-collector-contract.md`, L27 и исходный `scripts/codex-unix-boundary.py` на 2026-11-06. `PreparedPeer(dist, codex_js)` создаёт изолированный peer **до** старта проверяемого unit; `peer.ci_config` должен попасть в целевой процесс при запуске. `peer.collect(unit, port, expected_artifact_sha256, expected_full_artifact_sha256)` затем проверяет работающий unit; его допускается вызывать однократно, завершение контекста очищает собственный peer. При исключении либо отказе в проверке после переключения — существующий fenced rollback, при отсутствии готового collector/verifier — отказ до мутаций. Darwin collector пока не определён.

Текущий collector предназначен для отдельного Linux test stand, выдаёт `scope=installed-codex-consumer`, `status=INCOMPLETE`, `allRequiredScenarios=false`, `artifactEvidenceStatus=unverified-provenance`; одного Codex недостаточно. Нет подтверждённого безопасного production доступа, полного состава applicable harnesses и доверенного verifier, который проверяет происхождение и связь квитанции с этой конкретной транзакцией, generation/PID, проверенным payload и dependency closure. SHA inventory не доказывает загруженные модули. Квитанция не является разрешением на rollout. Без определения и доказательства этих границ нельзя заменить preflight безусловным успехом или счесть любое поле PASS достаточным.

Промежуточный patch `evidence/l30-fail-closed-receipt.patch` от текущего integration baseline устраняет потенциальное принятие возвращённой incomplete квитанции: пока verifier отсутствует, всякий ответ collector отклоняется и существующий rollback срабатывает. Это не подключение настоящего collector и намеренно не открывает выпуск. RED `evidence/l30-incomplete-red.log`: синтетическая incomplete квитанция после подменённого preflight ошибочно приводила к accepted в Linux/Darwin. GREEN `evidence/l30-incomplete-green.log`: обе платформы откатывают с проверкой fencing. L19 preflight tests 6/6; `git apply --check` к integration baseline проходит. Настоящий collector и общий runner остаются за Rawls и Tesla; их файлы не менялись.

Для следующего шага Rawls должен предоставить проверенный production-safe lifecycle/интерфейс peer и подтверждённый формат полного результата для всех применимых сред; владелец release должен подтвердить доверенный источник и привязку identity/digest к транзакции. После этого интегрировать создание peer до unit start и проверку результата перед acceptance, пройти RED/GREEN для несоответствий и реальную изолированную проверку через rollout. Не выдавать заранее сформированную или синтетическую квитанцию за installed proof.
