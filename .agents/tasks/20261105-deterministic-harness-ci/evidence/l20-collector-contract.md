# L20: контракт collector для L19

Модуль `scripts/codex-unix-boundary.py`, класс `PreparedPeer(dist, codex_js)` — Linux, один запуск, только Codex:

1. `with PreparedPeer(candidate_dist, codex_js) as peer:` создаёт приватный peer и временную конфигурацию; `peer.ci_config` доступен до запуска или рестарта целевого unit. Сокет и проект принадлежат этому запуску.
2. Вызывающий код запускает или переключает свой unit с `AGENT_HERDER_NATIVE_CI_CONFIG=peer.ci_config`; collector сам не запускает, не рестартует и не останавливает целевой unit.
3. После запуска `peer.collect(unit, port, expected_artifact_sha256)` проверяет systemd MainPID, starttime, loopback listener и payload до и после действий, проверяет идентичность peer, две сессии, завершённую доставку, проект, поиск, transcript и обращения к лжемодели. Ошибка — исключение; `collect` одноразовый и UNKNOWN не повторяет.
4. Выход из `with` очищает принадлежащие peer процессы и временные файлы. При смерти управляющего процесса launcher получает SIGTERM; после SIGKILL временная директория может остаться и требует проверки отдельным безопасным уборщиком.

Возвращаемая квитанция имеет `scope=installed-codex-consumer`, `harness=codex`, `allRequiredScenarios=false`; это не полный postdeploy gate. SHA покрывает dist и package manifests двух пакетов, не весь fleet bundle; байты уже загруженных модулей отдельно не аттестованы. MainPID должен быть самим Node `dist/index.js`: bootstrap/wrapper unit пока не поддержан.

`peer.test_environment()` и тестовый HTTP-токен предназначены только для отдельного стенда с пустым HOME и CODEX_HOME. Нельзя подставлять их в production unit: безопасный поиск CI-сессий в общем production процессе и доступ к адресному MCP без реальных ключей ещё требуют отдельной реализации. Стендовый PASS не разрешает production rollout. Если сборщик недоступен — отказ до switch; если сбой после switch — fenced rollback. При интеграции собрать доказательства всех применимых сред; не выводить `allRequiredScenarios=true` по одной Codex-квитанции.

### L20: отдельный MCP и wrapper, 2026-11-06

`x-herder-native-ci` направляет `/mcp` в CI runtime; поиск использует только ID, закреплённые созданием в этом runtime, и читает сообщения через изолированный Codex adapter. Общий индекс не используется. Поиск ограничен последними 1000 сообщениями каждой сессии и не доказывает полноту общего поиска. Ошибка peer или неверный CI token закрывает маршрут. `unitProcessChain` связывает systemd MainPID и listener по родительской цепочке, UID и starttime; вся цепочка сравнивается до и после consumer.

`receipt-l20-production-shaped-wrapper-stand.json` — только отдельный synthetic test stand на server-44: независимая HOME, синтетические settings/auth и foreign session, shell-wrapper + Node, две сессии Codex и локальная фиктивная модель. Синтетические файлы совпали по хэшу до и после collector. Исполняющий Herder unit не был изолирован файловой системой или сетью; обнаружен синтетический cache метаданных моделей, весь внешний трафик не прослежен. Поэтому квитанция не доказывает OS-запрет чтения production store/ключей, отсутствие любой внешней сети или работу установленного production unit. Обычный production token был синтетическим; его enforcement на внешнем интерфейсе отдельно не проверялся. До гарантии отсутствия доступа к production данным необходим отдельный изолированный production-mode тест с проверкой OS-границ и трафика. Результаты других сред отсутствуют: `allRequiredScenarios=false`.

Следующая проверка sandbox: `l20-mount-sandbox-red.log` показывает отказ `uv_os_get_passwd` при пустом `/etc`. Синтетический `/etc/passwd` устранил этот отказ, но `l20-pid-sandbox-red.log` показывает отключение CI-конфигурации в отдельном PID namespace. Отдельный локальный эксперимент на server-44: UNIX `SO_PEERCRED` для процесса за пределами PID namespace вернул PID 0; текущий `inspectNativeCiPeer` требует положительный PID. Это объясняет несовместимость текущего внешнего peer с таким PID sandbox, хотя журнал намеренно скрывает точную причину конфигурационного отказа. CI-доставка в этих RED запусках не начиналась. Следующий шаг — создать peer в общей PID namespace с Herder при сохранении отдельной сети/mount peer и проверить peer UID/PID/starttime, доступ к production путям и сетевые запреты; не ослаблять проверку peer.

CLI LHC 1.15.0 `progress ... L20` отклонил новую запись как просроченную, потребовав закрыть и разбить leaf. Поскольку эта граница ещё не доказана, L20 не закрыт фиктивно; результаты сохранены здесь и в квитанции.

Обновление контракта L21: `PreparedPeer.collect` теперь дополнительно требует `expected_full_artifact_sha256`, вызывает `native-ci-artifact-identity.py` до и после consumer для candidate root и root из PID entrypoint, сверяя оба digest и относительный `agent-resume` entry; при отсутствии digest или несовпадении отклоняет запуск. Передавать следует digest из доверенного candidate CI, а не произвольный boolean. Пока нет реализованного проверенного reader/provenance evidence, сопоставления платформы/Node flags/NODE_PATH и полного доказательства closure; возвращается `artifactEvidenceStatus=unverified-provenance`, `allRequiredScenarios=false`. Inventory на диске и отдельный Node `require.resolve` не доказывают байты модулей, уже загруженных PID. Новая версия collector с этим контрактом на реальном unit ещё не прогонялась; квитанция выше относится к прежнему частичному fingerprint. Вопреки исторической заметке L21 локальный `tests/test_native_ci_artifact_packaging.py` сейчас GREEN (1 тест), но конкретный release и его evidence не проверены.

До наличия доверенного evidence и полного набора applicable harnesses collector возвращает общий `status=INCOMPLETE`, отдельно `codexScenarioStatus=PASS` для пройденного среза. Поле не является разрешением для rollout.
