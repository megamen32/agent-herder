# Предпросмотр отправленных сообщений и выбор режима доставки

Прямой запрос владельца08.10: каждое отправленное сообщение немедленно появляется в видимой очереди/предпросмотре со своим состоянием. Можно выбирать «В текущий ход» (native steer; голосовое tier) либо «После ответа» (queue, ждёт завершения хода). В настройках сохраняется предпочтительный режим по умолчанию. Несколько подряд отправленных задач сохраняют порядок и текст; нельзя молча терять/дублировать сообщение или выдавать HTTP-admission за native delivery.

Статус: локализация существующих API/renderer/persistence. Root владеет composer, frontend preference/outbox и минимальным actual route transport изменением, если оно необходимо. Другие UX/source задачи сохраняются; no AutoFind changes, new harness daemons, native group restart or Telegram notifications.

Важно: автоматическая межагентная доставка активному агенту через steer — отдельное ранее подтверждённое требование. Пользовательский explicit queue должен дождаться окончания хода; настройка человека не меняет режим межагентной координации. Для native receipt необходим стабильный inputId. Состояния «Отправляется», «Ожидает окончания ответа», «Доставлено»/«Не удалось» должны соответствовать реальной admission/completion семантике.

Приёмка: настоящий браузер отправляет несколько разных сообщений; список появляется сразу до завершения сети, сохраняет каждое сообщение и подтверждение/ошибку. Проверить переключение обоих режимов, сохранение предпочтения после reload и путь native active/idle на том же ID без нового harness. Проверки bounded, global/project locks, existing budget; keep shared native deployment blocker explicit.

Actual source localization: App.sendMessage in src/web-ui/main.tsx hard-codes mode queue, clears the draft only after API completion and blocks textarea/send while sending=true. There is no submitted-message preview/outbox; finally resets sending but catch does not present a failure. Existing actual src/web/server.ts message route already maps mode steer to options.steer and queue to options.queue, but does not forward inputId. Codex adapter supports native turn/steer; human queue collides with current writer and SessionSupervisor stores it as deferred rather than proving completion-triggered delivery. ZCode sendMessage ignores steer and only has its separate native sendPrompt/queued flush mechanism; do not offer a fake universal steer switch or label generic accepted HTTP as Delivered. add-settings skill was inspected; its concrete storage layers belong to video_watching and are not applicable here. Use Herder existing per-browser UI preference persistence for the person's default, not another project's TOML/DB.

Remaining work: persistent frontend submitted previews and per-message mode, true serial native completion-triggered human queue with stable inputId/receipt and failure reconciliation through the actual registered API, capability-backed steer, settings default persistence and real-browser multi-send/reload proof. Backend transition needs the already-recorded safe shared-ZCode handoff; no groups are restarted to unblock this requirement.
