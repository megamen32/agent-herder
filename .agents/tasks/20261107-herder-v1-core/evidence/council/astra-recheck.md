## Необходимые конкретные поправки

1. **P0 — INSTALL должен зависеть от принятого финального digest, а не только завершения FIX.** Сейчас граф R1 → native lanes/NEG → R2 → FIX → INSTALL. После FIX мог измениться source/runner, но повторная сборка и приёмка нового candidate явно не заданы. Дописать acceptance FIX/INSTALL: если bytes изменены, CI строит новый immutable manifest, выполняет affected-lane/NEG delta проверки; все пять результатов относятся к нему либо имеют обоснованное переиспользование неизменных components/config. INSTALL разрешён только при PASS обязательных операций 5/5 и NEG, без UNKNOWN/UNSUPPORTED/UNAVAILABLE в обязательных ячейках. Если FIX ничего не менял, сохраняется прежний digest. Завершение R2 с «реальными gaps» не является разрешением установки. Отдельный новый большой цикл не нужен — это выходной критерий существующего FIX и входной критерий INSTALL.

2. **P0 — окна времени не соответствуют leaves.** После завершения lanes в23:55 граф требует пять последовательных листьев по15мин: R2 → FIX → INSTALL → READBACK → R3, то есть до01:10. Даже если все lanes закончить в23:40, получится00:55. Это сумма заявленных оценок, не утверждение, что каждый шаг обязательно займёт все15мин. Поправить существующие оценки/зависимости по реальной работе: R2/R3 должны быть короткой фиксацией уже собираемых receipts, FIX — условным и включающим re-gate; установка/readback имеют защищённое время. Не сжимать consumer gate на бумаге ради попадания в срок. Для пяти15-минутных lanes за30мин нужна подтверждённая ёмкость минимум трёх независимых lane executors/процессов; owner=CI не доказывает такой параллелизм. Указать ссылки на реальные CI lanes/resources, не создавать дубль исполнителей. Дедлайн00:38 остаётся, отсутствие такого расписания означает NEEDS_EVIDENCE по сроку.

3. **P0 — OpenCode second deliver является ранним функциональным решением, не поздним сюрпризом NOC.** CONTRACT признаёт v22 initial-only; запись B10 также говорит, что v2 допускает existing-session queue/steer, v22 fresh-only. B12/NOC должны назвать exact native family/version из manifest и сохранённый результат второго input в той же session. Не выбирать v2 молча для зелёной проверки v22; при выборе поддержанной v2 явно ограничить доказанную совместимость этой версией. Если обязательна v22 и второй input недоступен, lane остаётся незавершённой; повтор initial create не заменяет deliver. Решение нужно до R1, исправление legacy остаётся у CI, wrapper только экспонирует поддержанное поведение.

4. **P1 — исправить буквальное равенство request_key и native inputId.** Фраза «Один request_key передаётся в native inputId» слишком сильна: существующий ZCode `zcodeInputId` добавляет `agent-herder:auto:` для automation; Codex receipt различает inputId/turnId. Заменить на: «core request_key детерминированно и устойчиво связывается с adapter inputId и возвращёнными native message/turn IDs; read/restart не генерируют новый идентификатор и не dispatch-ят повторно». В A11/B12 проверить exact mapping и различие accepted/completed/UNKNOWN. Не синтезировать native receipt из произвольного request_key. Existing journals сохранять; их namespace должен соответствовать instance/native session, а не случайно совпавшему ID соседнего экземпляра.

5. **P1 — сделать межworker read contract проверяемым коротким примером.** CONTRACT задаёт названия методов и raw bytes, но A10/B10/D10–D12 имеют одинаковую общую acceptance. В существующий контракт/приёмку добавить точные request/result examples для listSessions/getRawTranscript/listProjects, schema версии common transcript и формат ошибки при превышении frame. Для projects: native либо подтверждённый registry с provenance/coverage; отсутствие listProjects не превращается в успешный пустой список. Для export: required format и многостраничный sample фиксируются до PASS; oversized error честен, но не закрывает требование full transcript для такого sample. Для search: ACL-visible marker после ingestion, исключение закрытого scope и declared coverage. Это предотвратит три несовместимых трактовки у disjoint workers без переработки протокола.

## Минимальное закрытие recheck

Достаточно внести эти точечные условия в существующие CONTRACT/leaf acceptance и evidence: (a) окончательный digest + post-FIX gate, (b) согласованный остаток времени с реальной CI ёмкостью, (c) exact OpenCode version/second-deliver outcome, (d) стабильное отображение receipt IDs, (e) один согласованный read wire sample. Никакой новый найм, scheduler, release route или большой roadmap не требуется.

Для installed gate сохранить обычный потребительский клиент: если целевому harness нужен существующий translator, проверить этот путь.
