Проверен профиль именно `AHAP_CODEX_BIN` + `AHAP_CODEX_CWD` + `CODEX_HOME` (socket отсутствует) на тех же проверенных байтах `5ea28f`. Лог и сохранённый профиль: `codex-v1-5ea28f-bin-preflight-01.log` и `codex-v1-5ea28f-bin-preflight-01/home/authority/profile.json`. Это отдельная только preflight попытка, старый UNKNOWN и ранее отклонённый create не повторялись.

Точный контракт композиции: `src/adapters/codex-app-server.ts::startProcess` передаёт pinned binary в `spawnIsolatedWorkload`; Linux `src/workload-launcher.ts::buildDetachedWorkloadCommand` исполняет его через `systemd-run --user --scope`. В существующем `tests/native/launch.py` bwrap не монтирует user D-Bus, для `XDG_RUNTIME_DIR=/run/user/0`, `DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/0/bus` отдельная read-only проверка той же команды `systemd-run --user --scope --quiet --collect ... /usr/bin/true` вернула exit 1: `Failed to connect to bus: No such file or directory`. Эта проверка подтверждает несовместимость launcher и обязательного workload launcher; общий `phase=init, cause=Remote` сам по себе не содержит конкретной внутренней ошибки. Подключение внешнего host bus не доказывает, что systemd создаст child в сетевом namespace fixture: такой обход не выполнялся. Флаги VITEST/workload-isolation-off через core env не передавались.

Provider contract: официальный пример https://developers.openai.com/siwc/token-sharing-open-source/codex-app-server показывает, что custom `model_provider` может использовать токен ChatGPT plan даже при `requires_openai_auth=false`. Следовательно ни имя custom provider, ни этот флаг не являются надёжным признаком отсутствия subscription. В текущем adapter guard использует имя модели и не умеет доказать effective provider/identity запуска. Для поддержанного безопасного пути нужны существующий или product-owned контракт запуска direct child внутри гарантированного netns (без host systemd manager), а также provider identity, подтверждающая локальный fixture endpoint и native PID/namespace.
