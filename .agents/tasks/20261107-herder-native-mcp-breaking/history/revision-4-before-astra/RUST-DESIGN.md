# Agent Herder: новая реализация на Rust

Ревизия 4, 7 ноября 2026. Предыдущий план отклонён владельцем. Его исходные документы сохранены в history/rejected-r1. Действующий список работ — WORKPLAN.md и R-листья LHC.

## Решения

1. Новый daemon, доменное ядро, CLI и адаптеры — Rust. Официальный MCP SDK — rmcp 3.9.0 с закреплённым Cargo.lock. Первая сборка проверяет совместимость выбранных crate features и toolchain; обновление зависимости — отдельное осознанное изменение.
2. Wire protocol — MCP 2026-07-28, стандартные Tasks, subscriptions, Skills и input_required. Номер TypeScript SDK v2 больше не является требованием к реализации на другом языке.
3. Ровно 17 продуктовых инструментов. Никакого собственного job/operation API, скрытых legacy handlers и protocol downgrade.
4. Архитектура не зависит от server-100/44/88/104, домена, каталога пользователя, systemd или конкретного браузерного профиля. Топология и экземпляры задаются конфигурацией.
5. Каждый исполнимый лист имеет конкретный результат, проверку, вход и оценку не более 60 минут. Весь цикл расписан сейчас; больших стадий «детализировать потом» нет.
6. Обследования старой архитектуры и инфраструктуры исключены. Сохранённые ошибки используются как требования и регрессии. Подключение конкретного клиента и проверка конкретного target выполняются в соответствующем листе, а не отдельным проектом инвентаризации.
7. Перепись не означает удаление native histories, чужого WIP, ручных остановок и исходов уже принятых действий. Для Herder state — одноразовый импорт с explicit reconciliation; постоянная совместимая прослойка не сохраняется.

## Почему Rust

Для обычного сервиса orchestration Go был бы предпочтителен по простоте реализации и сборки. Для этой задачи решающий фактор — готовность обязательных MCP расширений.

Выполнена ограниченная проверка официальных SDK, без чтения старой архитектуры Herder:

- Go SDK v1.8.0 заявляет MCP 2026-07-28. В просмотренных 25 production Go-файлах пакета mcp на main не найдены tasks/get, skills/list и идентификаторы Tasks/Skills. Это свидетельство пробела выбранного SDK, а не утверждение, что на Go невозможно их реализовать.
- В опубликованном Rust SDK rmcp-v3.9.0 присутствуют model/task.rs и model/skill.rs с типами стандартных расширений. В официальном репозитории также есть TaskManager, subscriptions и tests Skills/Tasks. Это уменьшает объём работы, который иначе пришлось бы вложить в SDK.
- Rust даёт строгие типы состояний и компиляторную проверку владения памятью. Он не доказывает корректность distributed delivery, идемпотентности, отмены или permissions: для них нужны явные контракты и тесты.
- Цена — более сложные async/ownership и более медленные сборки. Сдерживаем её одним приложением, конкретными DTO, обычными trait boundaries и готовыми библиотеками; без универсального plugin framework, сложной типовой магии и custom runtime.

## Компоновка приложения

Один модульный daemon, а не набор микросервисов. Один Rust binary запускает сервер и CLI. Статические Web UI assets и Skills включаются в поставку; frontend остаётся браузерным TypeScript/JS и не требует Node runtime у daemon. Нативные Codex/Claude/другие harness — внешние продукты со своими зависимостями.

Основные модули:

```text
config / auth / domain
application: общие операции и правила
adapters: отдельная реализация каждого продукта
store: SQLite, Tasks, intents, holds и настройки
mcp: SDK, schemas, resources, subscriptions, Skills
peer: тот же MCP transport между нодами
cli / web: клиенты общих application services
```

Tokio — сеть и async I/O. Blocking filesystem/SQLite работа выполняется вне async executors через ограниченный blocking pool/выделенный writer. Не держать mutex guard через сетевой await. Все очереди ограничены; timeout/cancellation передаются по context. FTS и ingest работают порциями. Shared task state не копируется в отдельный job engine.

SQLite используется как embedded хранилище на ноде для Tasks, переписки и индексов; каноническое владение release/checkout хранится в JSON по RECOVERY-STORAGE.md; не вводить обязательный внешний DB/Redis/Kubernetes. Настройка peers и instance profiles достаточна для одной машины или нескольких сетей. Для межнодового доступа — объявленный доступный endpoint с аутентификацией; NAT traversal и auto-discovery всего интернета не обещаются.

Целевые ОС поставки: Linux и macOS, amd64/arm64. «Любая инфраструктура» здесь означает независимость от конкретного флота и топологии на поддерживаемых ОС. Windows и другие ОС не заявляются работающими без отдельной сборки и native проверки.

## Идентичность и владение

Node содержит много HarnessInstance; каждый instance имеет adapter type, profile, connection, capabilities и доступные сессии. Адрес — node_id + instance_id + native_session_id; наружу session_ref. Нативный ID и название harness отдельно недостаточны.

Instance ID переживает рестарт своего профиля, но не копируется при клонировании нового профиля. Runtime host и workspaces сессии разделены. Смена записи cwd не считается переносом работающего процесса. Нода назначения владеет native connection и повторно проверяет авторизацию/дедупликацию.

Capabilities: поддерживаемая операция и ограничения. Availability: сейчас ли экземпляр доступен. Permissions: имеет ли вызывающий право. Эти три ответа не объединяются в boolean supported. Невозможное действие сообщает причину и конкретный допустимый следующий шаг.

## MCP и состояние операций

Применяются server/discover, per-request capabilities, стандартные task methods, subscriptions/listen, skills/list/get и resources/read согласно выбранной ревизии. Неподдерживающий клиент получает объяснение до side effect. Секреты не передаются аргументами инструмента и не попадают в diagnostics.

Tasks дают внешнюю форму длительной операции. Её durable backend хранит связь с native admission. Повтор request key с тем же payload возвращает исходный receipt; с иным payload — conflict. Неизвестный исход не перезапускается. tasks/cancel не означает, что принятое внешнее действие физически отменилось.

После disconnect subscription клиент переподписывается и читает актуальный ресурс. Не обещать exactly-once события. При backpressure — resync, а не бесконечный буфер. Skills загружаются через стандарт, применение инструкций доказывается в клиенте отдельно.

## Ошибки и понятность

Диагностируемая ошибка сообщает поле/состояние, received, expected, correction, effect и retry policy. Ошибки schema приходят из выбранной action-ветки, не из всех веток union. Corrected call валидируется той же схемой и использует только известные данные. Неизвестный target требует discovery, не выдумывается.

Пример смысла ответа: «paths недопустимо для workspace action=declare; для резервирования используйте action=reserve. Действие не начато. Вот исправленный вызов с вашим session_ref». Форма нового declare закрепляется в его typed schema, а не наследуется от старого facade.

Неизвестный результат: «Запрос мог быть принят. Повторно не отправляйте. Прочитайте исходный Task/receipt по этой ссылке». Forbidden не предлагает обход. Internal error даёт diagnostic ref, без выдуманного совета. Native/server/transport errors сохраняют причины по всем границам, включая Hub.

session recent содержит две роли, timestamp, message/turn refs, truncation и полноту. Отсутствие данных не является пустой историей. Remote transform не отбрасывает content. Transcript resource доступен вызывающему через разрешённый маршрут; чужой локальный filepath не заменяет выгрузку.

## Проверка результата

Все проверки входят в рабочие листья WORKPLAN.md. Фиксированный native CI использует настоящие harness и локальный deterministic model endpoint. Gemma отдельно проверяет usability инструментов и ошибок в свежих контекстах без исходников. Browser fixture не закрывает реальные ChatGPT/Z AI lanes.

Обязательны: два одинаковых harness на ноде; одинаковые native IDs в разных instance; две ноды с произвольными адресами; ошибки в schema через настоящий MCP; последние сообщения по ролям; полная pagination; Task restart/cancel; UNKNOWN; stop/deliver race; cron DST; slow subscriber; denied auth; installed artifact identity и обычный consumer.

Критические сценарии не допускают неправильного адресата, опасного retry или ложной полноты. Число tool/model calls и фактический usage записываются, когда доступны; символы не выдаются за токены.

## Полный рабочий план

См. WORKPLAN.md. Все активные R-листья — реальные bounded задания, по 30–60 минут, с входом, результатом, приёмкой и областью изменений. Нет листа «переписать все адаптеры» или «развернуть весь флот». У каждого адаптера отдельно: соединение, чтение, отправка, transcript, управление и native приёмка.

Тематические заголовки служат навигацией и не имеют собственных многочасовых оценок. Сумма усилий не является календарным ETA. Если лист оказался больше часа, исполнитель возвращает конкретную границу неизвестного и делит работу до исполнения; оценка не продлевается молча.

Один интегратор владеет общими схемами и ядром. Адаптеры разных продуктов выполняются параллельно после готовности их входов. Параллельные листья одного каталога получают одного владельца либо отдельные непересекающиеся файлы. Публикация в main по правилам проекта, только owned paths; чужие изменения сохраняются.

В текущем LHC writer жёстко зашит старый предел 15 минут. plan_cli.py использует тот же канонический atomic writer и меняет только в своём процессе процедурный предел для этого каталога на прямо заданные владельцем 60 минут. Общие файлы LHC и другие планы не изменяются. Старые отклонённые L/M листья имеют deferred и сохраняют исторические оценки; в действующий объём входят только R-листья.

## Удаление старой реализации и поставка

Новый Rust сервер строится отдельно, старый TypeScript daemon не используется как backend. Перед переключением выполняется одноразовый импорт нужного состояния с проверкой holds/intents/UNKNOWN; перепись не требует сохранять старый API.

Web UI, CLI, hooks, LHC, Hub и остальные перечисленные потребители получают явные bounded изменения. Удаляются old aliases/handlers, jobs API, _async команды, CDP-only exports, fixed browser_wake, cadence и старые launchers. Отрицательные вызовы доказывают отсутствие callable legacy; одной проверки tools/list недостаточно.

Installer получает artifact, paths, endpoint и профиль как параметры. Проверка target непосредственно перед установкой защищает данные и соседей; это эксплуатационный preflight, не архитектурное обследование флота. Lease/fence/CAS сохраняются до проверенной замены. Текущие native сессии не прерываются без соответствующей необходимости и полномочий.

Rollback проверяется с учётом записей после переключения. Простой возврат старой БД, который повторит доставку или снимет stop, недопустим. Старый отключённый артефакт для отката не является legacy endpoint нового сервера.

Завершение: один точный release candidate прошёл required native/client проверки, затем Linux/macOS installed consumer, независимую приёмку, публикацию main и runbook. Дополнительные выбранные ноды получают отдельные установочные задания <=60 минут. Неподтверждённая обязательная интеграция остаётся открытой, не заменяется fixture PASS.

Статус: пересмотрены только план и документация. Реализация и делегирование в этом ходе не начаты.

## Ревизия 4: отказ MCP не лишает агентов владения

Обязателен [контракт файлового storage](RECOVERY-STORAGE.md). На объявленной машине JSON ownership является источником истины для MCP и автономного recovery CLI. Отсутствующий owner в подтверждённом storage позволяет немедленный атомарный claim без назначения человеком. Из SQLite не восстанавливается старый owner. Skill/manifest доступны локально до первого MCP-вызова; context snapshots имеют явную давность. R142–R149 доводят текущий план до 149 задач и 138.5 инженерного часа; все листья <=60 минут. Число MCP-команд остаётся 17.
