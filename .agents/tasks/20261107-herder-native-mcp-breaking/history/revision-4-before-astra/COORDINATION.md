## Данные, которыми владеет Herder

1. **Идентичность.** session_ref, node_ref, instance_ref и native ID. Self берётся из проверенной привязки клиента к сессии; общий токен ноды не доказывает identity конкретного агента. Недостаточная привязка даёт caller_identity_missing с способом подключения. Переданный произвольный session_ref не разрешает выдавать себя за его владельца.
2. **Происхождение.** created_by (session/human/service/unknown), native_parent_ref, created_at, creation_request_ref, provenance. Создатель сохраняется при принятии намерения создать сессию; после native admission связь дополняется фактическим ID. Создание из другой среды/ноды поддерживается. Родство не выдаёт права и не назначает руководителя. Последний отправитель не заменяет создателя. Внешняя сессия с неизвестным происхождением остаётся unknown.
3. **Корреспонденция.** message_ref, sender principal и verified sender_session_ref, recipient_ref, in_reply_to, request_key, content/resource_ref, время, native receipt и состояние доставки. Журнал хранится вне transcript/model context. Для native сообщений, прошедших мимо Herder, полнота и неизвестный отправитель отмечаются явно.
4. **Проект и рабочее место.** project_ref независимо от локального пути, repository identity с provenance, worktree_ref, node/path, branch, declared scope, текущая задача, observation time и lease. Связь checkout с проектом задаётся явно или подтверждается Git-данными; basename и похожий заголовок недостаточны. Отдельные clones не становятся одной физической блокировкой; shared filesystem требует одного workspace authority.

Родство и переписку хранить в общем SQLite store и стандартных ресурсах. Каноническое владение release/checkout хранится в JSON по RECOVERY-STORAGE.md; SQLite-проекция не является authority. Журнал сообщений — предметные данные; собственный API задач/job не возвращается. Политика хранения явная: после удаления текста метаданные/квитанция и tombstone сохраняются согласно retention, чтение сообщает утрату содержимого. Ни поиск, ни контекст не раскрывают чужие закрытые сессии.

## Понятные вызовы: число команд остаётся 17

| Вызов | Описание |
|---|---|
| `session(action="context")` | По проверенному self возвращает: кто я, кто создал, native parent, дети, последние собеседники, сообщения и курсор продолжения, проект, соседи и рабочие деревья, конфликты, coverage, freshness и готовые допустимые следующие вызовы. |
| `session(action="messages", direction="inbound", cursor=...)` | Читает сохранённые входящие сообщения и отправителей. Доступны outbound и чтение конкретного message_ref. Чтение не отправляет сообщения и не подтверждает их понимание моделью. |
| `deliver(reply_to=message_ref, message=..., request_key=...)` | Отвечает проверенному отправителю конкретного сообщения. Адрес вычисляет сервер; получатель исходного сообщения должен соответствовать вызывающей сессии. Конфликт явного target с reply_to отвергается до отправки. |
| `deliver(session_ref=..., message=..., request_key=...)` | Пишет создателю или выбранному соседу по сохранённому адресу. Отправитель определяется сервером. |
| `list_sessions(project_ref=...)` | Показывает участников проекта во всех известных рабочих деревьях/нодах: цель, состояние, пути, scopes и давность наблюдения. |
| `workspace(action="claim", workspace_ref=..., expected_version=...)` | Атомарно занимает рабочее место либо возвращает конфликт, владельца и способ перейти в отдельное дерево. Renew/release используют выданный токен и fencing version. |

Синтаксис здесь — контракт для R006/R008, не действующий API старого сервера. Обычный `session` сохраняет recent user+assistant по умолчанию. `context` ограничен по размеру, сообщает omitted_count/cursors/resource refs; полные сообщения читаются отдельно. Безопасный пример ошибки: «Общее дерево уже занято сессией S. Ваш запрос ничего не изменил. Создайте отдельный Git worktree, зарегистрируйте его через workspace и повторите claim для нового workspace_ref». Ответ содержит доступный адрес S и корректный вызов чтения; права доступа проверяются до раскрытия.

## Автоматическая осведомлённость

При создании, подключении, возобновлении и поддерживаемом событии компакции адаптер передаёт краткую карточку: собственный session_ref; создатель; проект; доступные соседи с целями и деревьями; конфликты; точный вызов session(context). Изменения публикуются через стандартные подписки; bridge клиента доставляет их в допустимый native контекст. Простая подписка сервера не считается доставкой модели.

После очистки контекста новая context generation получает полный краткий snapshot, даже если fingerprint серверных данных не изменился. При отсутствии native compact hook — карточка перед следующим поддерживаемым ходом/ответом инструмента и явное session(context). Capability отдельно показывает механизм автоматической доставки. Нельзя заявлять автоматическое восстановление в клиенте, который вообще не предоставляет точки инъекции; ручной read остаётся доступен.

Delta не запускает новую модельную задачу, не снимает HumanStop и не создаёт бесконечный цикл ответов. Пропущенные события восстанавливаются snapshot по cursor/version. Доставка в текущий ход проверяет его актуальный native ID. Значимые изменения объединяются; heartbeat не рассылает весь список заново. Observed/injected/answered — разные состояния, «прочитано и понято» сервер не выдумывает.

## Как выбирать рабочее дерево

Список соседей информирует, claim разрешает кооперативное владение. При единственном участнике и успешном claim можно работать в основном checkout, если политика проекта разрешает. При занятом checkout создаётся собственное дерево, затем регистрируется и резервируется. Herder сообщает факты и предоставляет reservation; создание Git worktree и решение о merge принадлежат workflow/LHC.

Два одновременных claim одного checkout имеют одного победителя. Авторитет для workspace единственный; отказ MCP допускает claim через независимый файловый маршрут к тому же authority (RECOVERY-STORAGE.md). Недоступность самой машины/storage запрещает новый claim, а не создаёт локального второго владельца; независимая работа продолжается. TTL lease не доказывает остановку процесса: после потери lease запись прекращается у соблюдающих протокол клиентов, незавершённый процесс/dirty state требует reconciliation. Herder не обещает физически запретить произвольному shell писать в файлы.

Пустой список с неполным coverage означает «известных соседей нет; часть источников недоступна». Даже полный список не назначает агента руководителем проекта и не разрешает присваивать чужой WIP. На разных деревьях показываются также пересечения объявленных scopes, чтобы агенты согласовывали дизайн заранее.

## Обязательная приёмка

- A создаёт B в другом harness: B без истории знает A и отвечает; native parent может отличаться от created_by.
- C пишет B: после очистки model context и рестарта Herder B восстанавливает A и C, читает исходное сообщение и отвечает C через reply_to. A остаётся создателем.
- Одновременно две сессии видят пустой roster и запрашивают один checkout: один claim успешен, второй получает понятный конфликт и работает в отдельном дереве.
- Два Codex с одинаковым native ID в разных instances и две ноды сохраняют правильные адреса; потерянная нода делает coverage неполным.
- Повтор request_key, разрыв между admission и receipt, истёкший lease, потерянная подписка, STOP и недоступный отправитель не приводят к дублю, подмене адресата или самовольному пробуждению.
- Свежий агент без исходников восстанавливает общение только по описаниям инструментов и ответам; результат подтверждён в реальном клиенте. Fixture отдельно проверяет детерминированные гонки; не заменяет native доказательство.
