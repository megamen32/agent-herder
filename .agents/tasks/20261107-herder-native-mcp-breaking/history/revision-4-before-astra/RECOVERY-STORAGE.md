# Каноническое файловое хранилище и работа без MCP

Ревизия 4, 2026-11-07. Обязательный контракт новой реализации. Число MCP-инструментов остаётся 17. Процедуры ниже проектируются; это не действующие команды установленного Herder.

## Результат для пользователя

Если daemon/MCP Herder сломан, агент по заранее установленной инструкции обращается к известной машине и каталогу, читает JSON и занимает свободное владение без обращения к человеку. MCP и файловый маршрут видят одного и того же владельца. После восстановления daemon принимает фактическое состояние хранилища.

Отсутствие owner-файла в подтверждённом хранилище означает: владелец не назначен, можно немедленно попытаться занять роль. Владельцем становится победитель атомарного claim. Две сессии, одновременно прочитавшие отсутствие файла, не становятся двумя владельцами.

## Один authority, два маршрута доступа

При установке явно задаются storage_id, authority node, абсолютный root, версия схемы и независимый доступ к машине (локальный filesystem или разрешённый SSH). Хотя бы одна машина содержит канонический storage; имя машины и пути параметризуются. По умолчанию один authority обслуживает настроенные проекты. Автоматическое назначение запасной машины при partition отсутствует.

MCP handler и автономный CLI используют одну файловую библиотеку и один authority. На удалённой ноде оба обращаются к тому же authority. Не создавать новый fallback-owner в SQLite, Git ref или локальной копии каталога. Известные старые fallback writers удаляются/переводятся при cutover; отключение MCP не меняет протокол владения.

Для ownership JSON является источником истины всегда. SQLite хранит Tasks, correspondence и индексы; ownership там может быть только восстанавливаемым представлением. Перезапуск сервера не записывает поверх JSON сохранённого ранее владельца из БД. Таким образом не требуется транзакция записи одного owner в две независимые базы.

## Файловый контракт

Пример относительных путей внутри явно заданного root:

```text
storage.json
projects/<project-id>/project.json
projects/<project-id>/release/owner.json
projects/<project-id>/release/state.json
projects/<project-id>/release/guard.lock
projects/<project-id>/workspaces/<workspace-id>/owner.json
projects/<project-id>/workspaces/<workspace-id>/state.json
projects/<project-id>/workspaces/<workspace-id>/guard.lock
projects/<project-id>/snapshots/context.json
RECOVERY.md
```

`storage.json` и `project.json` — обязательные маркеры правильного, инициализированного storage/project. `state.json` содержит durable generation/fence и последнюю квитанцию перехода; не удаляется при release. `guard.lock` — стабильный inode для OS-lock, его не удаляют и не заменяют. `owner.json` существует только при назначенном владельце; отсутствует после освобождения.

Owner JSON содержит schema_version, storage_id, project_ref, resource kind/ref, owner principal и session_ref (если подтверждён), claim_id, generation, acquired_at, expires_at и описание цели. Никаких credentials. Claim ID обозначает запись, а полномочия на изменение следуют из проверенного доступа к authority; знание ID не даёт доступ.

Установленный manifest на каждом разрешённом клиенте содержит точный authority, root, storage_id, ссылки на Skill/RECOVERY.md и команды чтения/claim с уже подставленными несекретными параметрами. Его путь публикуется в инструкциях клиента. Manifest доступен до первого вызова MCP. Изменение authority — явная передача с остановкой writes и обновлением клиентов; старый authority отказывает в writes после передачи. Обычный перенос storage не выполняется автоматическим recovery.

## Что означает отсутствие файла

Признак свободного владения — успешное чтение правильных storage/project маркеров и подтверждённый ENOENT конкретного owner.json на authority. Timeout, permission denied, неверный storage_id, повреждённый JSON, отсутствующий root/project/state, отключённый mount и недоступная машина дают разные ошибки, а не «владельца нет».

Это условие касается только соответствующей роли: отсутствие release owner не делает агента руководителем всех сессий и не разрешает трогать чужой WIP. Отказ чтения блокирует только требующее исключительного владения действие; чтение исходников, разработка в своём дереве и другая независимая работа продолжаются.

## Атомарность и восстановление после сбоя

Файловая библиотека на authority берёт OS-lock стабильного guard.lock, перечитывает state/owner, проверяет полномочия и expected generation, записывает prepared переход в state, атомарно публикует owner через temp+fsync+rename и завершает переход в state. Fsync каталога обеспечивает durable rename/unlink. Каждый переход имеет request_key; повтор после потери ответа возвращает прежний исход. Повреждённый файл не считается отсутствующим.

При падении между записями следующий процесс под тем же lock завершает или сверяет prepared переход по claim_id/generation. Читатель, увидевший незавершённый переход, получает конкретную команду reconcile; не придумывает свободного владельца. State хранит монотонный fence после освобождения owner. Вложенные пути строятся по проверенным идентификаторам; symlink/path traversal не допускаются.

Автономный recovery CLI запускается без daemon, MCP SDK transport, БД и LLM. Он умеет status/claim/renew/release/reconcile, возвращает JSON и понятное русское объяснение. Это отдельная точка входа небольшого установленного бинарника `herder-recovery`, использующего файловую библиотеку. Готовый бинарник и инструкция лежат у authority и не требуют работающего installer/сети для сборки. Прямое чтение JSON возможно обычными файловыми средствами; обычное изменение выполняется готовыми командами, чтобы агенту не требовалось самостоятельно программировать locking.

## Release и workspace

Общий `workspace` получает resource kind `checkout|release`; отдельных MCP release-lease инструментов не появляется. LHC получает release ownership через этот контракт, при отказе MCP — через те же действия автономного CLI.

Истёкший lease допускает takeover по правилам ресурса, без разрешения человека только из-за отсутствия владельца. Для release выполняющая действие обёртка удерживает execution guard на authority на всё время эффекта; активный guard не допускает takeover, даже при просроченном heartbeat. Child process должен удерживать guard при смерти родителя. Каждый поддерживаемый release entrypoint сверяет claim/fence и expected deployed revision. Для удалённого эффекта его runner проверяет fence либо обеспечивает единственного исполнителя; одна проверка в начале удалённого shell-скрипта не считается достаточной.

При оборванной связи ранее принятый внешний release может иметь UNKNOWN исход. Читается квитанция/реальная версия, автоматически сверяется состояние; действие не отправляется повторно вслепую. Это ограничивает конкретный неизвестный эффект, а не всю разработку проекта. Проверка квитанции должна работать независимо от MCP Herder.

Для checkout lease сообщает кооперативное владение; сам по себе не запрещает произвольному процессу писать на диск. После утраты lease соблюдающий протокол клиент прекращает запись, чужой dirty state сохраняется. Recovery не удаляет чужие деревья.

## Какие данные можно читать без MCP

Канонические owner/state читаются непосредственно. Для сессий, создателей, рабочих деревьев и адресов собеседников публикуется атомарный JSON snapshot с generated_at, source revision, coverage и признаками неизвестного. Эти snapshots — проекции SQLite, их давность видна. В них нет секретов и текстов закрытых переписок; ACL ограничивает проект/принципала. Они помогают восстановить адреса и координацию, но не считаются живым roster и не являются квитанцией доставки.

Новая отправка сообщений через файловую очередь в scope не входит. После восстановления MCP переписка читается из существующего durable journal. Это сохраняет единственную процедуру доставки и запрет повторять UNKNOWN.

## Описание MCP и Skills

Короткая инструкция сервера и описания workspace/nodes содержат подставленные storage_id, authority, абсолютный путь manifest/owner и правило:

> При отказе MCP используйте указанный файловый storage через локальный доступ или SSH. Если storage и проект подтверждены, а owner.json отсутствует — роль свободна: выполните атомарный claim. Получив claim, продолжайте без запроса назначения у человека. Команды и восстановление после сбоя — в Skill herder-recovery и локальном RECOVERY.md.

Длинные схемы JSON, примеры ошибок, stale-owner recovery и процедуры идут в Skill, предоставляемый механизмом Skills выбранной ревизии MCP. Тот же текст поставляется локально с плагином/CLI; клиент знает путь заранее. Получение инструкции только через сломанный MCP недопустимо. Установленные копии имеют версию/хеш и берутся из одного исходника.

Ошибка чтения содержит: какой storage/path проверялся, какой результат получен, что можно сделать дальше и что осталось доступным. Пример: «SSH доступен, но root не содержит storage.json с ожидаемым storage_id. Владение не определено. Проверьте manifest по указанному локальному пути; независимая работа в вашем дереве может продолжаться».

## Обязательная приёмка

1. Полностью выключить daemon и MCP. Новый агент с установленными инструкциями находит authority, читает JSON, занимает свободный release и завершает разрешённый тестовый release без вопроса человеку и без обращения к Herder DB.
2. Одновременно claim через MCP и recovery CLI: ровно один владелец. После включения daemon оба маршрута показывают того же owner/fence.
3. Kill writer до/после prepared state, rename, unlink и финального state; reconcile восстанавливает однозначное состояние, повтор request_key не создаёт новое владение.
4. Проверить различие owner ENOENT, неверного пути, permission denied, недоступного authority и corrupt JSON. Ни один из последних случаев не выдаёт ложный claim.
5. Просроченный owner без активного execution guard освобождается/заменяется по контракту; живой release guard и устаревший fence не допускают конкурентный release. Потерянный ответ не повторяет эффект.
6. При недоступном Skill по MCP локальная инструкция достаточна агенту без чтения исходников. Старый fallback writer не создаёт второго источника владения.
