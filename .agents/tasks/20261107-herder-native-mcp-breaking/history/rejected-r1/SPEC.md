# Agent Herder: полный цикл breaking change

Дата: 7 ноября 2026, Europe/Moscow. Статус: спецификация для передачи исполнителям; реализация не начата.

## 1. Решение владельца и граница поручения

Владелец согласовал единый интерфейс адаптеров, capabilities, ноды с несколькими независимыми экземплярами одного harness, удаление legacy и полный цикл поставки. Дополнение: использовать MCP 2026-07-28 и SDK v2, стандартные Tasks, subscriptions и Skills over MCP. Собственный публичный operation/job API не нужен. Ошибки обязаны объяснять конкретное исправление.

Текущее поручение — подготовить полный план и спецификацию. Запуск реализации и рассылка исполнителям в этом ходе не выполняются. Следующий руководитель получает этот документ и граф LHC; старые открытые планы не становятся автоматически его поручениями.

Исходный согласованный каталог из 18 команд сокращён до 17 за счёт operation. Общие свойства не сокращаются ради числа команд. Новая команда требует самостоятельного пользовательского действия, которое нельзя выразить текущим контрактом или стандартом MCP.

## 2. Исходные свидетельства

1. `src/mcp/tool-consolidation.ts` сохраняет старые зарегистрированные обработчики вызываемыми и сокращает только discovery. Есть две ветки `workspace action=declare` с разными схемами. Требуется заменить саму архитектуру, а не ещё один фасад.
2. `src/types/harness-runtime.ts` содержит registry по HarnessType; `src/mesh/fleet-node.ts` ищет адаптер по названию harness. Этого недостаточно для нескольких профилей одного harness на одной ноде.
3. Чат `01a1ac52-d25c-7050-a65d-3fca32642c26`, host `remote-ssh-discovered:104.bezrabotnyi.com`, прочитан ограниченно, два последних хода. Источник — текущие сообщения и существующий план `20261105-deterministic-harness-ci`, а не вся 22-часовая история.
4. В приложенном там эпизоде `workspace declare` возвращал `Invalid input`; модель меняла hostId, хотя лишним полем было `paths`. Последнее уточнение исполнителя: `ttlSeconds` само по себе допустимо; не закреплять раннюю ошибочную диагностику.
5. `session_info` обещал последнее сообщение, но читал карточку. В удалённом ответе сообщения дополнительно терялись при преобразовании. Из CI-чата перенять доказанные fixes после проверки их точного commit/diff, не считать их уже установленными.
6. Чат требует recent user + assistant по умолчанию, compact только явно и понятный путь к полной истории. `read_message` не является универсальным чтением транскрипта.
7. По локальному снимку CI-плана L43: diagnostic PASS не равен candidate/release PASS; отсутствовали required lanes и installed identity. L51 и L60 остаются входными зависимостями, состояние перепроверить при исполнении. Browser fixture не доказывает ChatGPT/Z AI.
8. Точный расход токенов ошибочного эпизода не подтверждён. Не заменять usage числом символов и не обещать конкретную экономию.
9. Checkout содержит чужие изменения в адаптерах, transcript, CDP, consolidation и CI. Их не откатывать и не включать в собственные коммиты. Активный CI имеет отдельного владельца.

- https://ts.sdk.modelcontextprotocol.io/v2/servers/skills

SDK v2 и wire revision — разные версии. Зафиксировать точные версии зависимостей и lockfile; не писать плавающий «latest». В M01 сохранить нормативные ссылки и версии использованных схем. Skills на прочитанной официальной странице обозначены Beta; поддержка SDK attach также требует проверки точной версии.

Для 2026-07-28 использовать `server/discover` и capabilities в метаданных каждого запроса. Не переносить автоматически старую initialize-centric схему. Стандартные ошибки и структура ответов соответствуют выбранной ревизии. Авторизация обязательна независимо от stateless транспорта.

### Tasks

Расширение `io.modelcontextprotocol/tasks`: `tasks/get`, `tasks/update`, `tasks/cancel`. Сервер может вернуть `resultType: task` на tools/call, если клиент заявил capability в данном запросе. Итоговый результат находится в стандартном Task. Не изобретать tasks/result, job_get, operation или суффиксы `_async`.

Отсутствие необходимой capability: стандартная ошибка `-32021`, `requiredCapabilities` и объяснение, что обновить в клиенте. Нельзя начать побочный эффект и лишь затем обнаружить, что клиент не сможет получить его результат.

MCP задаёт контракт Task, но не реализует native delivery, идемпотентность, хранение состояния и расписание за Herder. Один durable backend хранит задачи и привязанные намерения доставки; отдельная параллельная job state machine запрещена. Нативный UNKNOWN не превращать в completed. В рамках разрешённых статусов MCP возвращать корректный результат/ошибку с указанием неизвестного исхода и ссылкой для сверки. Отмена Task не доказывает отмену уже принятого нативного действия.

### Подписки и ресурсы

Использовать `subscriptions/listen`, подтверждённый сервером фильтр и стандартные уведомления. Состояние сессии, проекта, workspace, настроек и transcript доступно через resources/read. Проекты — отдельный тип ресурса с каталогом и ссылками из list_sessions; новая команда ради списка проектов не нужна.

После разрыва — переподключение, подписка и повторное чтение авторитетного ресурса. Не обещать exactly-once уведомления или replay, которых не обеспечивает выбранный транспорт. Дедупликация изменений по версии ресурса, ограничение очереди медленного клиента и явная необходимость resync. Удаление и изменение прав также корректно инвалидируют ресурсы. Нет отдельного публичного event_list и постоянного LLM-polling.

### Skills и вопросы человеку

`io.modelcontextprotocol/skills`: skills/list, skills/get, ресурсы SKILL.md и связанных файлов через resources/read. Реализовать manifests/digests и права доступа по стандарту. Чтение файла не означает активацию skill клиентом. Проверять отдельно discover, read и фактическое применение клиентом.

Короткий базовый skill: выбрать экземпляр → создать/найти сессию → доставить → проверить результат → прочитать recent/полную историю. Отдельные инструкции для администратора и для coordination/autopilot доступны по требованию. Описания инструментов достаточны для простого вызова без предварительного прочтения всех skills.

Вопрос, необходимый для выполнения текущего MCP-вызова, использует стандартный input_required/elicitation, включая Task при необходимости. `human_request` сохраняется только для самостоятельного вопроса человеку, привязанного к управляемой сессии и внешнему каналу Notice Place. Он не дублирует MCP elicitation и не хранит второй lifecycle поверх Task. Нативные permissions чужой сессии — предмет `permission`, не произвольный ответ вызывающей модели за человека.

## 5. Доменная архитектура

Node → HarnessInstance → Session. Adapter — реализация возможностей типа продукта; экземпляры имеют отдельные профили, native storage, авторизацию и соединение. Код не использует HarnessType как уникальный адрес.

- node_id стабилен между рестартами; instance_id стабилен для конкретного профиля/подключения; native_session_id принадлежит экземпляру. Непрозрачный session_ref отображает тройку, но не даёт прав доступа сам по себе.
- На клон instance identity заводится заново; перенос identity допускается только управляемой миграцией. Повторные node/instance ID обнаруживаются до маршрутизации.
- Runtime location и рабочие пути различаются. Сессия может работать на нескольких удалённых машинах; cwd не служит её единственным адресом.
- Native owner один на экземпляр. Повторное подключение не создаёт второго writer/controller. Нода назначения проверяет полномочия и дедупликацию до native admission.
- MCP, CLI, Web UI и межнодовые запросы вызывают одни application services. Удалённый маршрут не имеет альтернативных правил остановки и доставки.
- Три разных факта: adapter supports, instance currently available, caller allowed. Capabilities описывают ограничения, причины unavailable и наблюдаемую версию.
- Каталог инструментов и схемы определены в одном месте; адаптеры реализуют доменный интерфейс и не регистрируют свои публичные команды.
- Общий error mapper сохраняет причины всех границ; adapter-specific детали остаются внутри безопасной диагностики.

Native APIs предпочитаются чтению файлов. Файловое чтение, где это реальный доступный источник, находится в адаптере и учитывает профиль, XDG, WAL, версию схемы и ограничения полноты. Поиск не запускает model turn и не экспортирует все истории при каждом запросе.

У named create область уникальности — instance + canonical workspace/project + name. Совпавшие названия на разных нодах не выбираются автоматически. При неоднозначности возвращаются допустимые кандидаты, без угадывания.

## 6. Контракт ошибок, которые помогают исправить вызов

У каждой ожидаемой ошибки есть стабильный machine code и короткое человеческое объяснение. Для неверного ввода: конкретное поле/JSON path, безопасно показанное полученное значение, ожидаемая форма, причина, точное действие исправления. Для нескольких ошибок возвращать ограниченный список всех независимых замечаний выбранной ветки. Не выдавать всю пачку неотносящихся ошибок union.

Обязательная информация по смыслу (в error.data или structured tool result по спецификации, без самодельной оболочки вокруг всего MCP):

```json
{
  "code": "INVALID_ARGUMENT",
  "message": "Поле paths недопустимо для workspace action=declare.",
  "issues": [{
    "path": "/paths",
    "actual": "array of workspace paths",
    "expected": "отсутствие поля в этом действии",
    "fix": "Для объявления укажите workspaces; для резервирования используйте action=reserve."
  }],
  "effect": "not_started",
  "retry": "after_correction",
  "next_action": {"tool": "workspace", "arguments": {"action": "reserve", "session_ref": "<тот же подтверждённый адрес>", "paths": ["<исходный путь>"]}}
}
```

Это пример структуры диагностики, а не окончательный JSON Schema workspace. Конкретный corrected call генерируется из утверждённого контракта, сохраняет проверенные поля исходного запроса и проходит его валидацию. Если target неизвестен, возвращать безопасный discovery call, не выдуманный ID. Секреты/закрытые targets в actual и suggestions не попадают.

Обязательные классы: неизвестный инструмент/действие, лишнее/отсутствующее/неверное поле, неоднозначный instance, unsupported capability, unavailable node, forbidden, conflict/stale revision, missing MCP capability, expired cursor/task, partial history/search, busy target, HumanStop, external outcome unknown, internal failure. Для внутреннего сбоя — безопасный diagnostic ref и способ проверить состояние; не выдумывать исправление.

Стандартные protocol/validation errors сохраняют стандартный JSON-RPC code; доменный code — в предусмотренных данных. Ошибки исполнения tool обозначаются по стандарту. Нельзя менять code -32602 или -32021 произвольным строковым значением. Проверить, что SDK validation middleware не отрезает описание до попадания к модели, включая gateway и клиент.

`retry` различает never, after_correction, after_state_change, safe_same_request. UNKNOWN: только сверка исходного Task/native receipt, без рекомендации повторить действие. Permission denied не советует обходить разрешения.

Дескриптор каждой команды содержит цель, минимальные обязательные поля, default поведение, побочные эффекты, reference-поля и следующий способ чтения. Ошибки и примеры формируются из одной схемы. Простые вызовы не требуют изучать внутреннюю топологию.

## 7. Чтение сессии, транскрипта и поиск

session get по умолчанию возвращает последний запрос пользователя и последний ответ ассистента отдельно, с message ID, timestamp, role, turn ID при наличии и полями truncation/completeness/source. Если ответ ещё не относится к последнему запросу, это видно по turn/timestamp. Последний commentary не представляется финальным ответом. Отсутствие чтения — unavailable/unknown, а не пустая история.

compact явно включается и не читает transcript. При усечении recent возвращается ресурс чтения остатка; полный transcript доступен через export_transcript. Ресурс удалённой ноды читается вызывающим через авторизованный маршрут, не возвращается недоступный локальный path как якобы полученный файл.

Пагинация привязана к session+instance+snapshot revision. Нельзя использовать cursor другой сессии. Общий формат сохраняет роли, порядок, части сообщений, tool calls/results, ссылки на вложения и unknown native content. Native raw доступен отдельно. Завершённая выгрузка имеет проверяемый конец и counts/digests, частичная — явную причину.

Поиск использует один источник индекса на профиль, учитывает существующие OpenCode v2/XDG и Hermes WAL fixes. Контракт сообщает охват источников; `partial=false` имеет доказательство, а не default. Неполученная нода не исчезает из результата молча.

## 8. Автоматизация и владение

HumanStop переживает рестарт и не снимается свойством humanRequested, которое любой агент может подставить. Снятие требует аутентифицированного человеческого/административного действия по действующей политике. stop фиксирует hold даже если native interruption недоступно; этот результат не называется полной остановкой.

autopilot имеет одну цель и одну стратегию продолжения на сессию. Native stop hook и observer не создают два продолжения одного turn. deliver, wake, cron и autopilot проходят общий gate и общий ledger.

cron хранит явное расписание/timezone, политику missed runs и concurrent runs. По умолчанию нет накопления просроченных запусков и перекрытия одного расписания. DST, изменение часов, рестарт и pause/delete во время admission тестируются. Текущие cadence не превращаются молча в новое постоянное расписание.

workspace декларация — информация; reserve — реальное временное владение. TTL/conflict/renew/release описаны и проверены; stale declaration не выдаётся за live process. LHC использует данные Herder и выполняет Git audit самостоятельно. Release lease сохраняет fencing и CAS в административном пути до проверенной замены; не удалять защиту деплоя вместе со старым инструментом.

settings объединяет desired/applied state и исключения. Общий automation hold — настройка с полномочиями владельца; не передавать bearer/token как обычный аргумент модели. Изменение имеет version precondition. Fleet revision status входит в ответ settings.

| common_settings*, fleet_policy_revisions, automation_disarm | settings + stop + проверка прав |

| session_queue | общие queue capabilities через session/deliver, без ZCode-only команды |

M01 строит полный машинный inventory всех registerTool, скрытых handlers, raw routes, aliases, external-adapters, CLI и SDK, а не ограничивается 46 видимыми именами. Каждая строка получает remove/migrate/internal с потребителем и проверкой. Не удалять пользовательскую возможность только потому, что её не заметили в tools/list. Новые несогласованные функции не добавлять; обнаруженное расхождение оформить конкретным решением владельцу до разрушения.

Архивная документация и changelog могут содержать старые имена; это не callable legacy. Новые инструкции, manifests, hooks и active clients не должны их вызывать. Прямые отрицательные вызовы проверяют удаление handlers, не только отсутствие имён в discovery.

## 10. Матрица окружений и потребителей

Для каждого адаптера отдельная строка, исполнитель и native acceptance: Codex, Claude, OpenCode, ZCode, Qoder, Hermes, Fast Agent, MiniMax Code, ChatGPT, Z AI, Browser Chat. Для каждого — inventory реальных версий/профилей, supported operations, read source, transport, authentication, lifecycle hooks, evidence, limitations. Нельзя закрыть весь ряд общей fixture.

Два экземпляра Codex на одной ноде обязательны; повторить изоляцию на другом доступном типе с несколькими профилями. Добавить два одинаковых native ID в разных instance как contract test. Межнодовой сценарий — отдельная пара нод. Linux и macOS — отдельные lanes.

Потребители: MCP direct и Hub/proxy; Web UI; CLI; native plugins/hooks; LHC; Notice Place; UserIO; ExManager/board; секретарь/BrowserWorker; CI producer/collector и release scripts; внешние адаптеры. В M01 подтвердить текущих владельцев, пути и реальные вызовы. Наличие в перечне не доказывает, что все развёрнуты сейчас.

Политика совместимости: только MCP 2026-07-28 в новом сервере; старый клиент получает понятный отказ до mutation. Не добавлять server-legacy shim и скрытый fallback. Для каждого требуемого клиента зафиксировать его поддержку revision, Tasks, subscriptions, Skills, input_required отдельно. Если внешний клиент невозможно обновить, это явный блокер соответствующей миграции; не объявлять всё завершённым и не возвращать legacy под другим именем.

## 11. Проверки и доказательства

### Детерминированный native CI

Переиспользовать существующий контур: настоящие CLI/app-server и Herder, детерминированный локальный model endpoint, изолированные профили/сеть/хранилища. Проверять create, two sessions, active turn, deliver, recent user+assistant, full transcript и search/projects. Контролировать фактическое число model requests и native admissions. Никакой подмены реального harness mock-адаптером для финальной приёмки.

Внешние браузерные сервисы, куда лжемодель неприменима, имеют отдельные реальные authorised lanes. Fixture используется для быстрых регрессий, но не закрывает их. Не брать личные чаты и не делать телефонные вызовы; вопросы/уведомления тестируются в изолированном адресате Notice Place. Если нужны голосовые тесты — только разрешённые Matrix test accounts, в этом проекте они не обязательны.

### Понятность для Gemma

Локальная Gemma — проверка usability выбора инструментов, а deterministic endpoint — проверка транспорта. Это разные проверки. Воспроизвести две предоставленные ошибки, затем дать новую задачу без исходников и без вручную подсказанного workflow. Замерять tool calls, неудачные повторы, корректность итогового ответа и реальные usage при наличии.

Минимальный фиксированный набор: 20 задач × 3 свежих контекста. Критические сценарии (правильный target, STOP, UNKNOWN, последние сообщения) — 100% без опасного действия и без выдуманной полноты. Для обычного выбора правильного инструмента — не менее 90% успеха; для исправимого validation error — минимум 95% случаев за один исправленный вызов, все обязательные эталонные ошибки должны исправляться. Непрошедшие случаи чинятся и повторяются; пороги не понижаются ради PASS. Успех модели дополняет, не заменяет детерминированную проверку схем. Seed/параметры и полный краткий trace сохраняются.

### Отказы и восстановление

Рестарт до admission, после admission до receipt и во время получения result; disconnect subscriptions; expired Task/cursor; недоступная remote node; busy turn; simultaneous stop/deliver/cron; потеря auth; смена модели без поддержки; локальное и удалённое обрезание сообщений; duplicate IDs; переименование профиля; clock/DST; slow subscriber; утрата terminal notification. У каждого теста ожидаемый observable результат и допустимое действие после ошибки.

### Производительность

Сначала baseline на зафиксированном корпусе/нагрузке, затем сравнение того же кандидата. Предварительные бюджеты при здоровой локальной ноде: p95 compact list/status ≤500 мс, p95 recent ≤2 с, p95 admission короткой команды ≤1 с; межнодовой бюджет включает измеренный transport RTT. Длительные операции быстро возвращают Task. Целевой полный deterministic native gate ≤5 мин при измеренной достаточной мощности; slow/browser lanes учитываются отдельно. Бюджет уточняется в M01 только с измерением и причиной, не после проваленного выпуска. Индексация не блокирует event loop; RSS/CPU без устойчивой утечки, отсутствие busy polling в idle. Искусственные общие server-100 quotas не восстанавливать.

## 12. Полный маршрут LHC

Оценки — инженерное усилие, не календарный ETA. Первоначальный ориентир по стадиям 83 часа; диапазон до инвентаризации 60–120 часов усилия. Доступность внешних браузерных аккаунтов и обновлений клиентов может добавить ожидание. Четыре рабочих слота — плановая ёмкость, не разрешение перегружать сервер. Модели исполнителей выбираются перед dispatch по актуальному каталогу; gpt-6 в графе — текущий плановый fallback, не утверждение о запущенных workers.

| Этап | Результат и выпуск | Зависимости | Оценка усилия |
|---|---|---|---|
| M01 | Контракты, inventory, error corpus, точные схемы, клиентская матрица, critique; релиз спецификации | — | 3 ч |
| M02 | MCP revision/Tasks/subscriptions/Skills и сквозной Codex; установленный изолированный стенд | M01 | 8 ч |
| M03 | Instance registry, owner routing, durable state, STOP/delivery/scheduling и общий контроль; релиз ядра на стенд | M02 | 12 ч |
| M04 | Каждый адаптер и его capabilities проверены native сценарием; отдельные стендовые выпуски | M03 | 20 ч |
| M05 | Потребители, skills, описания/ошибки, Gemma; выпуск потребителей на стенд | M03, финальные lanes используют M04 | 12 ч |
| M06 | Миграция данных, in-flight операций, репетиция cutover и rollback на копии | M04, M05 | 8 ч |
| M07 | Удаление legacy, один immutable RC, весь native gate и performance | M06 | 8 ч |

M01 заканчивается публикацией контракта, M02–M07 — выпуском на изолированный стенд. Production до готовности совместимой группы клиентов/нод не переключается. Это промежуточные результаты одного полного breaking change, а не уменьшение цели.

В графе подробно нарезается только ближайшая стадия; последующие — milestones с acceptance. Перед началом следующей стадии её работы превращаются в честные листья ≤15 минут; если native probe требует дольше, отдельно setup, admission, readback, анализ. Не обозначать многочасовой adapter rewrite одним пятнадцатиминутным листом. Для каждого harness/хоста/клиента — отдельные листья.

### Обязанности и параллельность

Lead владеет контрактами, приоритетом, общим кандидатом, разрешением коллизий, интеграцией и выпуском. Один владелец ядра ведёт shared types/schema/runtime; workers не меняют их независимо. Адаптеры после закрепления контракта работают параллельно в своих каталогах. Client workers используют контракт и candidate endpoint. Tester проверяет без чтения реализации, reviewer — границы и миграцию.

Предлагаемые зоны: protocol worker — MCP registration/standard extensions/errors; core worker — identity/routing/state; отдельные adapter workers; consumer workers по проектам; migration/release worker; независимый acceptance worker. Общий монолит session-supervisor/index.ts редактирует интегратор. Перед выдачей задания фиксируются exact paths и чужой WIP.

По прямому правилу проекта результат идёт в main; без отдельного указания не создавать feature branches. При параллельной работе использовать task-owned detached worktrees и отдельные run directories с точными базовыми SHA, затем согласованную интеграцию owned commits в main. Чужие ветки/изменения не удалять. CI-чат продолжает своё поручение; его изменения сначала проверяются и принимаются по точным receipts. Дублировать runner или отзывать его задания этот план не разрешает.

Каждое задание содержит: результат, входной контракт/commit, разрешённые файлы, исключения, RED→fix→GREEN для дефекта, native acceptance, способ запуска, ожидаемый артефакт и условия возврата. Закапываться в собственный новый planner/transport не разрешается.

### Точки независимой проверки

После M01: оспорить контракт на контрпримерах (два одинаковых harness, stale capabilities, remote resources, Task cancel после send). После M03: native fault injection. После M05: свежая Gemma и Zero Knowledge tester. После M07: проверка точного артефакта. После M08: проверка реального установленного потребителя независимым исполнителем. Независимая критика пока не выполнена; в текущем ходе workers не запускались.

## 13. Миграция и выпуск

1. Подтвердить актуальный inventory нод и профилей из ServersAdministartion и runtime. Не объявлять сервер из старого notes живым. Ноды оформляются отдельными листьями M08.
2. Зафиксировать исходные source SHA, runtime manifests, active sessions, queues, расписания, holds и owners. Сделать проверяемую резервную копию состояния. Данные native harness не удаляются.
3. На копии преобразовать IDs в node/instance/session; неоднозначные строки отклонять с отчётом. Перенести настройки, заметки, workspace ownership и HumanStop. Ключи остаются в защищённых исходных хранилищах.
4. Старые jobs привести к стандартному Task backend с сохранением outcome и native receipt. Terminal не переисполнять; UNKNOWN только сверять. Для in-flight недоступного native owner — явное unresolved состояние, не «успешная миграция».
5. Для cadence сформировать явное эквивалентное расписание или записать закрытый/остановленный статус по исходному состоянию. Не включать новые автоматические повторения при миграции. Неопределённое намерение — блокер именно этой записи.
6. Обновить required clients на стенде, подтвердить протокольные capabilities. Изменённые навыки/инструкции публикуются из единого источника. Каждый consumer получает явный список замены вызовов.
7. Собрать immutable artifact с major version и полным digest payload, включая bundle и реальные зависимости. Результаты отдельных snapshots не складываются в PASS другого кандидата.
8. Получить существующий release lease/fence; expected revision CAS; остановить новые automation admissions в мигрируемой группе, дождаться/сверить in-flight. Самовольное прерывание чужой работы не разрешается; требуемый простой описать по измеренной репетиции.
9. Установить группу клиентов/нод согласованно. Временно смешанные несовместимые версии явно отказывают, без скрытых мостов. Восстановить admissions после проверки адресации и состояния.
10. Для каждой ноды доказать artifact → loaded runtime/PID → native consumer. Проверить create/deliver/recent/transcript/search/projects, stop, Tasks, subscriptions, Skills через обычный клиент и UI reload там, где применимо.
11. При отказе остановить дальнейший rollout. Rollback не равен слепому возврату старой БД: после новых записей сначала сверка journal и state, чтобы не повторить delivery и не снять holds. Старый immutable release и backup доступны до окончания приёмки; они не подключены как legacy endpoint нового сервера.
12. После общего PASS публиковать main и release metadata по правилам проекта, удалить только task-owned временные среды и obsolete код. Рабочие данные и старые доказательства сохранить. Обновить inventory/инструкции/clients и передать эксплуатационный runbook.

## 14. Критерии завершения

- Полный авторизованный клиент обнаруживает ровно 17 продуктовых tools; нет callable old aliases, job API и protocol downgrade.
- Стандартные discovery, Tasks, subscriptions, Skills и input_required проверены фактическими клиентами, не только unit tests.
- Все обязательные adapter/consumer/host lanes имеют доказательства на одном финальном кандидате и затем на установленной версии; required unsupported lane остаётся blocker до решения владельца.
- Два однотипных instance изолированы; remote route и права корректны; restart не дублирует delivery; STOP сохраняется.
- Recent показывает обе роли; transcript полный либо честно partial; поиск не теряет источники молча.
- Ошибки видны модели сквозь SDK/proxy и позволяют исправить вызов; Gemma gate пройден.
- Legacy migrations имеют reconciliation report, rollback rehearsed; неопределённые внешние действия не повторялись.
- Все обнаруженные дефекты зарегистрированы и исправлены либо явно отложены владельцем. Нет автоматического переноса чужих baseline defects в PASS.
- main содержит только принятые owned изменения, remote подтверждён; фактические commits, артефакты, installed receipts и потребительские доказательства раздельны.
- План, SPEC, migration matrix, runbook и итоговый handoff согласованы; независимая приёмка выполнена.

## 15. Что остаётся уточнить до кода

Точные schemas 17 tools; перечень фактически активных клиентов/нод; capabilities их версий; доступный стандартный Task store в закреплённом SDK; пути исходников потребителей; attribution и migration conflict policy; полнота всех скрытых legacy routes; native smoke доступ ChatGPT/Z AI; baseline performance; доказанный standalone Git audit маршрут LHC. Это конечные задачи M01, а не разрешение бесконечно исследовать. Для каждой — вопрос, артефакт, ограниченный probe и решение, которое он меняет.

Рабочее решение: общий контракт и сквозной native путь. Идеальное: все адаптеры/потребители, протокольные расширения, понятные ошибки и полный отказ от legacy. Минимальный полезный промежуточный выпуск: MCP + реальный Codex на стенде; он не считается завершением поручения. В финал входят все согласованные обязательные свойства.
