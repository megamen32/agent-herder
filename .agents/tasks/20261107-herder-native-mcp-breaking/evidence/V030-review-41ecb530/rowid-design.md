# V030 indexed rowid seam — design and fixture

Snapshot `41ecb530`: `session_search_state(session_ref TEXT PRIMARY KEY, ...) STRICT` is an ordinary rowid table. The indexed primary-key lookup returns `rowid`, which remains the same across the current `ON CONFLICT(session_ref) DO UPDATE` (demonstrated). Assign that same ID as `session_search_fts.rowid`: SELECT/DELETE by rowid uses FTS virtual index `0:=`, not the `0:` full scan. No second store or registry is needed.

`rowid-probe.py` creates exact equivalent isolated schemas, populates both, and measures SQLite VM steps. At 100 and 10,000 documents respectively: state present 15/15, missing 10/10; FTS rowid present 30/30, missing 21/21. `EXPLAIN QUERY PLAN` confirms indexed state primary key and FTS rowid equality for read and delete. A changed document preserves all other documents; the same-key state upsert preserves rowid. This is SQL fixture evidence, not yet production Rust or native ingestion.

## Contract for Terra / schema owner

1. Existing v4 state rowids are **not** automatically equal to FTS rowids: fixture with state rowid 7 and FTS rowid 23 for the same session demonstrates this. Never interpret a v4 DB as satisfying the new invariant. Use an explicitly versioned migration, exact schema validation and writer fence under the existing canonical gate; rollback all DDL/data/version on failure. Old writer must be fenced, including its FTS write followed by guarded state write.
2. A hidden rowid of a table without an explicit `INTEGER PRIMARY KEY` is not a durable published identity guarantee across SQLite database maintenance/rebuild. Strong contract: make a stable declared `INTEGER PRIMARY KEY` in the authoritative state table, preserve unique `session_ref`, and use that PK as FTS rowid. Alternatively a formally guaranteed no-rebuild/no-rowid-change operational contract with fail-closed validation would be required and is weaker. This is a schema change; do not rely on observed VACUUM behavior as a guarantee.
3. One-time migration may scan: under exclusive transaction snapshot old state and FTS, verify at most one FTS row per session and account for orphan FTS, missing documents and malformed state. Rebuild FTS with `rowid=state_id` while preserving complete text/snapshot/truncated and ensure every present FTS row has exactly one matching state, and each state without a document remains distinguishable as missing/partial (or abort migration). Do not silently discard duplicate/orphan documents or pretend missing data complete. Check collision and full one-to-one invariant before version commit. For already-empty/new DB initialize the invariant directly.
4. Writer API in one transaction: indexed lookup by `session_ref`, use state PK; ensure FTS row at this ID is either absent or has exactly the same `session_ref` before any delete. Mismatched identity is corruption and must fail closed rather than delete another session's text. If equal snapshot and matching FTS, unchanged; if missing FTS rebuild from supplied complete snapshot; if changed, use direct FTS rowid delete and insert then guarded state update (or equivalent). New state insert obtains ID; state and FTS writes are atomic, with fencing exercised even on failure. No scan moves to coverage: the coverage query must look up state by indexed key and FTS by state ID, checking exact identity.
5. Validate targeted Rust updates for missing/new/changed/unchanged keys, unchanged other session ID/content/snapshot across reopen, transaction rollback and old writer fence, corruption/missing row and coverage, ACL before count/page, plus 100 versus 10,000 operation-count/query-plan regression. One-time migration scan is allowed; update is not.

The missing production feed remains independent: native source must provide a stable complete snapshot revision, signal partial/unavailable, and supply only the changed session; a real authorized consumer must exercise the result. No runtime corpus/live migration was touched.
