# Возобновление после других сессий

`resume_after` сохраняет одну просьбу: возобновить `owner`, когда закончится текущее нативное выполнение **всех** `dependencies`. У каждой сессии указывается harness и точный native sessionId. Один requestId используется для повторной отправки той же просьбы; для нового ожидания нужен новый requestId.

```json
{"owner":{"harness":"codex","sessionId":"parent"},"dependencies":[{"harness":"codex","sessionId":"worker-1"},{"harness":"opencode","sessionId":"worker-2"}],"message":"Продолжи интеграцию: fetch, merge, тесты и push.","requestId":"integration-1"}
```

Просьба не останавливает текущую сессию. Пока есть независимые задачи, она работает; доставка ждёт её свободного состояния. Native turn.completed/turn.failed или session.deleted дают подтверждение окончания. Один idle, запрос разрешения, отсутствие в списке и потеря соединения подтверждением не являются. Новый turn.started снимает предыдущее подтверждение. Завершение выполнения не доказывает качества: продолжившаяся сессия проверяет результат и Git.

`resume_after_status` читает ожидания, `resume_after_cancel` отменяет своё. Ручная остановка owner отменяет пробуждение. Циклические ожидания отклоняются: сначала опубликуйте готовые ветки/PR, затем ждите нужную интеграцию.

Состояние лежит в `~/.local/state/agent-herder/resume-after/` (один JSON на ожидание), переживает перезапуск и разрыв MCP. Запись о доставке сохраняется **до** вызова нативного транспорта. При неизвестном результате Herder запрашивает его receipt, а не повторяет действие. Сессия не объявляется завершённой только потому, что callback отработал.

Зависимость допустима только на harness'е, чей адаптер публикует нативные события хода: подтверждение окончания приходит из событий `turn.completed`/`turn.failed`/`session.deleted`, и без них окончание доказать нечем. События публикуют `opencode`, `codex`, `zcode`, `hermes` и `qoder`; `claude`, `fast-agent` и `chatgpt` их не публикуют — такая зависимость отклоняется при регистрации. Решает фактическая способность адаптера, а не список в схеме инструмента; ошибка называет harness и причину.

Используется существующий процесс Herder и его адаптеры. Отдельного демона, LLM-проверяющего или нового harness нет. Проверка готовых ожиданий раз в пять секунд не вызывает модель. Адреса относятся к адаптерам выбранного экземпляра Herder; одинаковые ID на разных хостах не считаются одной сессией.

Если нативное окончание произошло, пока Herder был выключен, и адаптер не воспроизвёл событие, ожидание остаётся неподтверждённым. Это видимо в status; отсутствие события не превращается в выдуманный успех.
