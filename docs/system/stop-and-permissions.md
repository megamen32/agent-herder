# HumanStop и нативные разрешения

## Что система делает сейчас

Rust хранит HumanStop в scoped authority. `stop` сначала фиксирует hold, затем при наличии нужной возможности запрашивает нативное прерывание; точные статусы эффекта представлены отдельно. Обработчики допуска и восстановления читают тот же gate. У слоя совместимости есть собственное хранилище HumanStop и код сопоставления с нативным ходом. `permission` работает с конкретным родным запросом, в том числе через совместимую Web-поверхность. ## Проблема

RPC может показывать живой либо прерванный ход, пока управляющий слой считает чат явно остановленным. Историческая запись о прерывании может относиться к другому ходу. Перенос ошибки модели, выключения процесса или состояния цели в HumanStop создаёт постоянную ложную блокировку. Несогласованные writer-ы создают обратный риск: один знает о Stop, другой ещё допускает отправку.

## Идеальная система

Владелец нажимает Stop один раз. Запись об этом действии тормозит автоматику до явного решения владельца, даже при рестарте. Обычное прерывание сохраняет возможность продолжить работу. Нативные запросы разрешения видны адресно, и ответ передаётся именно тому запросу, который показан человеку.

## Идеальный конечный результат

После Stop ни один автоматический путь больше не отправляет новый ввод в охваченную область. Та же сессия без подтверждённого Stop остаётся доступной для технического восстановления после сбоя. Экран состояния показывает источник ограничения и то, успел ли нативный движок прервать активный ход.

## Анализ по ТРИЗ

Противоречие по условию: нужно автоматически продолжать при сбое и полностью остановиться по воле человека. Цепочка ложной блокировки начинается с подмены подтверждённого действия косвенным статусом `interrupted`. Разделение по источникам даёт две функции: hold выводится из авторизованного действия, а вид нативного сбоя — из событий харнесса. Повторять разбор косвенной эвристики в интерфейсе, маршрутизаторе и каждом адаптере не требуется.

## Спецификация

1. Владелец scope хранит подтверждённое действие Stop, область действия и его поколение. Источник бывает явной командой владельца или нативным событием с достоверным признаком остановки человеком. Нативный родственный scope учитывается только по установленной связи. Цели, `errored` и общий `interrupted` сами по себе hold не создают.
2. Чистая проверка допуска принимает текущий hold и конкретный адрес действия. Сохранение hold сериализуется с handoff. Активный нативный interrupt выполняется только при наличии capability и точного адреса; возможность остановить будущие отправки отдельно видна даже при отсутствии нативного interruption.
3. Обычный `resume` и перезапуск процесса не снимают hold. Явное продолжение владельцем сверяет версию точной записи перед её снятием. Если поступил новый Stop, старое подтверждение не действует. Отдельная операция удаления или очистки для автоматического recovery не требуется.
4. Permission-решение проверяет владельца, адрес чата и ID ожидающего запроса. Одному запросу соответствует один принятый ответ; повтор читает конечный результат, устаревший ID не разрешает свежий запрос. [Вопросы человеку](human-requests.md)

## План и приёмка

1. Свести проверку источника Stop в один набор фактов у owner. Начать с [Codex recovery](../../crates/herder/src/adapters/codex/recovery.rs), [native stop](../../crates/herder/src/application/scoped_stop/mcp_stop.rs) и [ручного Stop в UI](../../src/human-stop-actions.ts). Инвентаризировать старые записи до переключения конкретного writer-а; сохранять подтверждённые hold.
2. В существующих тестах проверить: явный Stop переживает рестарт; смена состояния цели и `429` не создают hold; исторический abort другого хода не закрывает новую работу; в гонке `stop/deliver` допускается тот эффект, который первым получил право на handoff, и прекращаются последующие. Для разрешений — повтор ответа с тем же ID и отказ при устаревшем ID.
