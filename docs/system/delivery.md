# Доставка, очередь и квитанции

## Что система делает сейчас

Rust принимает `deliver.session`, `deliver.reply_to` и межхостовый конверт. Нода-владелец разрешает точный адрес, сохраняет intent и Task, затем передаёт ввод нативному адаптеру. Запись различает `prepared`, `dispatching`, `admitted`, `confirmed`, `rejected` и `unknown`. Идентификатор отправителя сохраняется в связанной квитанции. В TypeScript есть очередь отложенных сообщений и HTTP/MCP gateway очереди; отдельные харнессы также имеют собственную нативную очередь. [Обработчик Rust](../../crates/herder/src/application/scoped_stop/mcp_deliver.rs) · [Gateway очереди](../../src/session-queue-control-gateway.ts) · [Отложенные сообщения](../../src/deferred-messages.ts)

## Проблема

«Запрос принят», «ввод поставлен в очередь», «ввод появился в чате» и «модель ответила» происходят в разное время. Когда интерфейс сводит их к одному признаку или переключает writer при таймауте, человек видит зависание либо получает дубль. При совместной работе двух очередей ожидание в одной очереди легко принять за отсутствие работы в другой.

## Идеальная система

Обычная `deliver` возвращает ссылку на одну отслеживаемую операцию. Владелец чата знает, кто принял ввод, есть ли он в очереди и каким нативным сообщением или ходом он стал. Отправка, ожидание и чтение квитанции доступны независимо друг от друга.

## Идеальный конечный результат

Один и тот же запрос, повторённый клиентом или прокси после рестарта, возвращает ту же операцию. В нативном чате виден один ввод. Во время сбоя интерфейс показывает последнюю установленную стадию и продолжает читать статус этой же операции.

## Анализ по ТРИЗ

Здесь техническое противоречие между быстрым ответом клиенту и достоверным знанием о доставке. Цепочка «медленный адаптер → потерян ответ → клиент повторяет действие → второй ввод» разрывается разделением во времени: сразу вернуть идентификатор операции, а доказательство доставки записать по нативному ID. Разделение по уровням оставляет право отправки у owner. Прокси и UI читают его Task, поэтому собственная очередь повторов в них лишняя.

## Спецификация

1. Владелец чата проверяет адрес и права, атомарно регистрирует `principal + target + key + hash`, затем один writer выполняет внешний эффект. Состояние `prepared` означает доступную для исполнения запись. Чистое решение по снимку выбирает вернуть старую квитанцию, зарезервировать действие, сообщить конфликт или сверить результат. Нативный эффект выполняется через порт вне SQL-транзакции под существующей синхронизацией владельца.
2. Точный replay возвращает тот же `task_ref` и текущую квитанцию. Тот же ключ с изменённым содержимым даёт `idempotency_conflict` без нового эффекта. Причину ожидания очереди возвращает её владелец. Элементы очереди идентифицируются ключами, достаточными для адресного чтения или отмены.
3. Потерянный ответ после handoff остаётся `unknown` на том же запросе. Сверка использует квитанцию и точные нативные данные. Новый вызов отправки становится допустимым после свидетельства, что прежняя не началась. Неопределённость одной операции ограничена её областью, а параллельные чаты продолжают работу.
4. Квитанция различает приём ввода, создание нативного хода и результат модели. Политика восстановления модели использует последнее из этих наблюдений и свой эпизод. [Автовозобновление](recovery.md) · [Межхостовая маршрутизация](fleet-routing.md)

## План и приёмка

1. Локализовать расписание отправок и источник состояния очереди через [mcp_deliver.rs](../../crates/herder/src/application/scoped_stop/mcp_deliver.rs) и [session-queue-control.ts](../../src/session-queue-control.ts). Для каждого покрываемого режима показать конкретный owner и переход, который видит UI. Убирать повторяющийся dispatch только у поверхностей, уже выполняющих запись через общий owner.
2. Дополнить существующий [потребительский стенд](../../tests/native/ahap_opencode_consumer.py) сценариями: redo по тому же ключу после таймаута, изменение payload, рестарт между admission и readback, внешний Stop между подготовкой и отправкой. Проверить два не связанных чата при неопределённой операции в одном из них.
3. Приёмка выполнена, когда `deliver` и чтение квитанции обычным клиентом показывают одну операцию, один нативный ввод и точную причину ожидания; рестарт сохраняет все три факта. Для UI очереди переиспользовать [HTTP-тест](../../tests/session-queue-control-http.test.ts).
