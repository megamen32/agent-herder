# Ресурсы и аренды

Связанные контракты: [supervised jobs](../supervised-jobs.md), [execution scope](../project-execution-scope.md), [аренда S21](../s21-resource-ownership.md), [канонизация release claims](../canonical-release-cutover.md).

## Что система делает сейчас

Agent Herder хранит описания ресурсов и текущие claims в настроенной authority. Ресурс имеет тип и scope; claim связывает ресурс с владельцем, сроком, ревизией и execution binding. Acquire использует request key, обновление descriptor — CAS по revision. Advisory declaration worktree сообщает о работе, но не захватывает ресурс.

Supervised process может получить существующие claims как bindings. Worker продлевает аренды; терминальная квитанция сообщает результат процесса отдельно от доказательства освобождения ресурса. При неопределённом состоянии occupancy остаётся зарезервированным для reconciliation. Отдельная опциональная release occupancy capability по текущему контракту выключена по умолчанию; это описание исходников, не подтверждение конфигурации установленного runtime.

Scope проекта проверяется по канонической project identity и журналу намерения. Он ограничивает эффект границами проекта, а не просто путём, переданным вызывающим. Сопоставление release-ресурса с deployment target явное; aliases должны вести к одной authority и одному target.

S21 в Herder представлен только read-only статусом аренды на server-100. Сам телефон не является узлом Herder, API не предлагает claim/renew/release или управление устройством. Ошибка чтения означает unavailable, а не free.

## Проблема

Подтверждённой текущей поломки этого контура из доступных исходников не следует. Архитектурный риск: несколько поверхностей (ручной claim, process binding, release guard и старые ledgers) могут описывать один физический эффект. Ошибка в identity mapping или потеря доказательства завершения способна либо допустить конкурирующий эффект, либо надолго удержать ресурс.

Другой риск — смешать project scope с process scope: правильно ограниченный проектный запрос ещё не доказывает, что дочерний процесс не вышел за разрешённую рабочую область. Для S21 опасно трактовать недоступность источника как освобождение.

## Идеальная система

Одна настроенная authority владеет descriptor, claim generation, fencing и execution binding. Любой эффект сначала получает решение чистой политики по точным resource identity, principal, revision, claim и scope; затем совершает эффект через узкий порт с тем же fence. Наблюдение и advisory declaration не меняют владение.

Execution scope выводится из зарегистрированного проекта и конкретного execution, валидируется до первого эффекта и не расширяется из аргумента агента. Результат процесса не освобождает ресурс, пока доказано завершение всего контролируемого дерева. Потеря ACK или противоречивое наблюдение сохраняет UNKNOWN для той же операции.

## Идеальный конечный результат

Один конкурентный эффект на один общий ресурс; устаревший владелец не может продлить или освободить чужой claim. После подтверждённого завершения освобождается только связанная аренда. Неопределённый исход остаётся видимым и не превращается в повторный запуск. S21 статус честно различает held, free и unavailable.

## Анализ по ТРИЗ

Причинная цепочка: разрозненные идентификаторы одного объекта → разные ledger/lock → параллельный доступ либо ошибочное освобождение → потеря контроля над эффектом. Обратная крайность — блокировать ресурс до истечения TTL даже после доказанного завершения.

Противоречие: ресурс должен быть доступен быстро после завершения и одновременно оставаться закрытым при неизвестном состоянии. Это физическое противоречие жизненного цикла: освобождён и занят не вообще, а в зависимости от достоверного терминального свидетельства.

Принцип разделения — по состоянию и времени: активная аренда, терминальное доказательство и UNKNOWN представлены раздельно; освобождение разрешается только для точного claim generation после доказанного конца дерева. Функция «показать занятость» отделена от функции «разрешить эффект»; read-only статус S21 не получает полномочий управления.

Проверяемая польза: конкурентный claim для одного resource identity имеет единственного владельца; stale fence не изменяет состояние; UNKNOWN не открывает ресурс; доказанный terminal receipt освобождает только свой binding.

## Ресурсы

- **Вещественные:** настроенная storage authority, resource descriptor, OS execution lock, процессное дерево и receipts.
- **Информационные:** canonical resource ref, descriptor revision, claim ID/generation, principal, request key, execution ref, project identity, fencing token, boot ID и process start ticks.
- **Временные:** срок claim, deadline процесса и подтверждённый момент завершения; TTL сам по себе не доказывает прекращение эффекта.
- **Избыточные:** project aliases и advisory declarations полезны для навигации, но не создают authority.
- **Связанный ресурс S21:** внешний источник аренды на server-100; Herder получает ограниченное наблюдение и не владеет устройством.

## Спецификация

- **Владелец состояния:** существующая настроенная `StorageAuthority`; при sealed release cutover — canonical resource authority. Не MCP аргумент и не remote executor.
- **Чистое решение:** проверить principal, canonical resource identity, revision, claim generation, request key, execution binding и проектный scope; вычислить допустимый переход и следующий fence.
- **Эффект через порты:** атомарно записать transition в authority и захватить/проверить OS execution lock. Для процесса отдельно наблюдать дерево и записать terminal receipt; для S21 только читать существующий lease endpoint.
- **Одна проверка на правильной границе:** конкурентная попытка acquire на одной зарегистрированной identity проверяется внутри authority под её writer lock/CAS, до старта команды.
- **Наблюдаемый результат:** один активный claim и fence; отказ второму владельцу; для окончания — receipt с `tree_complete`; для неизвестного — `UNKNOWN` и сохраняющийся binding. S21 выдаёт free/held/unavailable без mutation.
- **Минимальные сценарии:** acquire и replay того же request key; конфликт изменённого payload; stale revision/fence; два владельца одного ресурса; процесс с подтверждённым exit и процесс с потерянным наблюдением; одинаковый physical resource с разными aliases; проектный запрос за пределами scope; S21 read success и source unavailable.

## План и приёмка

1. Сохранять canonical identity и единственную authority при регистрации, alias mapping и migration; legacy ledger переводить только по описанному sealed cutover.
2. Удерживать claim через supervised execution, пока terminal evidence не докажет конец дерева; reconciliation относится к исходному execution и claim.
3. Применять project execution scope до команды через существующий проектный журнал и адаптер; не выводить полномочие из cwd или произвольной строки.
4. Считать приёмку успешной, когда сценарии выше показывают единоличное владение, отсутствие replay, правильное освобождение и неизменность чужого ресурса. Source/checkouts не доказывают установленное поведение; для runtime нужен отдельный receipt установленного артефакта и consumer readback.
