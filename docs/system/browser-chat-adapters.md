# Адаптеры веб-чатов ChatGPT и Z.ai

## Что система делает сейчас

Общий Rust-слой обслуживает scoped sessions и страницы. В коде обоих провайдеров есть чтение, создание и доставка. Статус каждого действия зависит от capabilities экземпляра и привязки браузера. [Порт сессий](../../crates/herder/src/adapters/browser/sessions.rs) · [Протокол](../../crates/herder/src/adapters/browser/protocol.rs) · [ChatGPT](../../crates/herder/src/adapters/chatgpt/native.rs) · [Z.ai](../../crates/herder/src/adapters/zai/native.rs)

ChatGPT связывает явное `failed` в текущей ветке с нативным пользовательским вводом. Z.ai читает `last_run.status` и `history.currentId` отдельно; текущий ответ `recovery` не связывает их в подтверждённую пару. Live-приёмка в этом проходе не выполнялась. [Нативное чтение ChatGPT](../../crates/herder/src/adapters/chatgpt/read.js) · [Страница Z.ai](../../crates/herder/src/adapters/zai/page.js)

## Проблема

Сайты по-разному представляют аккаунт, ход и ошибку. Общий запрет при неполном recovery-сигнале лишает пользователя всех отправок. Пропущенный «Продолжай» оставляет каждую упавшую задачу ждать ручной работы. Отправка в чужой чат или поверх нового сообщения имеет другой конкретный ущерб. Эти случаи проверяются в разных действиях.

## Идеальная система

Обычная отправка работает в выбранном авторизованном чате. Для технического восстановления адаптер сообщает связь прерывания с последним вводом и выполняет одну команду общего Rust `SessionRecovery`. Общий слой владеет intent и квитанцией. Причина временной недоступности видна по конкретному действию.

## Идеальный конечный результат

Оба провайдера читают и отправляют в существующий чат через расширение. Поддерживаемое восстановление продолжает тот же чат своей моделью, одним вводом и нативной квитанцией. Явный Stop и новая работа владельца защищены. Зависшая квитанция сверяется по этому вводу.

## Анализ по ТРИЗ

Техническое противоречие между доступной отправкой и точностью автоматического продолжения. Цепочка «нет привязки причины сбоя → общий ограничитель → блокируется обычный send» разрывается разделением по условию. Для обычного send достаточно точного аккаунта и адреса, для recovery нужен также текущий элемент незавершённой работы. По уровням Rust решает, продолжать ли эпизод, а адаптер непосредственно перед кликом сверяет контекст страницы. Дублирующая браузерная политика retry и обходное чтение всех сообщений из этого действия лишние.

## Ресурсы

Доступны account-scoped страницы, native IDs, durable intents, HumanStop, receipts и capability в [ahap_opencode.rs](../../crates/herder/src/adapters/ahap_opencode.rs). Расширение и его границы описаны в [browser-extension](browser-extension.md).

## Спецификация

| Действие | Факты на границе эффекта | Результат |
| --- | --- | --- |
| Read | Профиль, account scope, нативный адрес. | История нужного аккаунта и граница страницы. |
| Send | Точная текущая страница чата, явный Stop и доступность composer. | Один ввод, его нативный message ID или отдельный статус квитанции. |
| Recovery | Те же факты плюс актуальная пара сбой/ввод, свободная очередь и отсутствие новой работы. | Один «Продолжай» на текущей модели. Веб-capability резерва выключена. |

Чистое решение о стадии остаётся в ядре. IO расширения проверяет текущий account/chat и выполняет нативное действие. Недостающая связь для recovery возвращает причину `failure_input_unavailable` для этого эпизода, с повторной оценкой при появлении наблюдения. Она не превращается в HumanStop и не влияет на обычное чтение или отправку. Если нативная отправка доказанно не началась, ядро может продолжить попытку. Потеря подтверждения после клика вызывает сверку по исходному ключу. [Контракт восстановления](recovery.md)

## План и приёмка

1. Через собственное расширение пройти обычную отправку и readback для каждого провайдера в [browser_adapter_smoke.py](../../tests/native/browser_adapter_smoke.py). С этой операции начать, когда жалоба состоит в том, что все сообщения не уходят.
2. Для ChatGPT переиспользовать пару `failed → user input` в [read.js](../../crates/herder/src/adapters/chatgpt/read.js) и её сверку в [composer.js](../../crates/herder/src/adapters/chatgpt/composer.js). Существующий [стенд](../../tests/native/browser_adapter_fixture.mjs) имитирует отказ `429` в состоянии веб-чата; он считает клики и нативные сообщения. Проверить success, HumanStop, более новый ввод, потерю ACK и сбой первой попытки.
3. Для Z.ai один раз прочитать состояние согласованного упавшего чата. Если [page.js](../../crates/herder/src/adapters/zai/page.js) может связать событие ошибки с текущим сообщением либо наблюдавшимся вводом, вернуть эту пару в [native.rs](../../crates/herder/src/adapters/zai/native.rs) и добавить один позитивный и один stale fixture. Если провайдер не даёт связи, зафиксировать точный недостающий факт и принимать обычные операции отдельно.
4. После установки подтвердить одну доставку в нужном аккаунте с нативным ID и независимым чтением. Наблюдение следующего реального сбоя закрывает отдельный критерий recovery.
