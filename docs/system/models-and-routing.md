# Модели, квоты и резервные маршруты

## Что система делает сейчас

Herder показывает модель, разрешённые проектом маршруты и наблюдаемую квоту. В совместимом контуре проектная политика и Codex reserve guard живут отдельно. В Rust recovery `select_route` выбирает сохранённую модель на первой стадии и проверяет разрешённый резерв только на соответствующей стадии. Официальная подписка Codex имеет свой guard. Подтверждённый сторонний `opencodex` обслуживается со своей квотой; состояние подписки к нему не применяется. [Проектная политика](../project-model-policy.md) · [Codex guard](../codex-quota-guard.md) · [Выбор маршрута восстановления](../../crates/herder/src/application/scoped_stop/session_recovery.rs)

## Проблема

Название модели, провайдер, фактический аккаунт и бюджет могут расходиться. Проверка чужого бюджета задерживает рабочий маршрут. Переход на резерв до попытки на прежней модели меняет параметры работы без необходимости. Если выбор закодирован в каждом адаптере, одинаковые сбои дают разное поведение по харнессам.

## Идеальная система

Для исходного чата сохраняется использованный маршрут. Herder проверяет только политику маршрута, который реально собирается использовать. Допустимый резерв выбирается общим решением с учётом фактической возможности адаптера и доступной квоты.

## Идеальный конечный результат

Временный `429` на стороннем маршруте проходит обычный повтор в том же чате после ожидания. Другой провайдер появляется только после зафиксированного сбоя повтора и при свежей подтверждённой квоте разрешённого резерва. Веб-чат продолжает работу своей моделью, даже если умеет только этот режим.

## Анализ по ТРИЗ

Техническое противоречие между продолжением работы и защитой лимита появляется, когда одна проверка применяется к разным бюджетам. Разделить по условию: квота относится к фактическому провайдеру, endpoint и аккаунту. Разделить во времени: проверять резерв только после сбоя основной попытки. Разделить по уровням: адаптер сообщает доступные действия и наблюдения, а ядро принимает решение о переключении.

## Спецификация

1. Функция выбирает маршрут из текущего действия, сохранённой модели, политики workspace, capabilities и снимка конкретной квоты. I/O получения снимка, ожидания и смены маршрута остаётся в портах. Причина `unsupported`, `quota_exhausted`, `observation_unavailable` или `not_permitted` доступна клиенту по выбранному маршруту.
2. Первая стадия сохраняет модель и провайдера. Для временного ограничения действует известное окно ожидания и политика исходного маршрута. Подписочный reserve guard проверяет официальную подписку, сторонний маршрут пользуется своим источником. Настоящее исчерпание бюджета учитывается по его родной политике.
3. Резерв выбирается по существующей конфигурации для этой области, при поддержке адаптером и положительной квоте его же аккаунта. Разрешение и доступная квота необходимы одновременно. Нарушение маршрута между проверкой и handoff отменяет только эту попытку. Отключение возможности смены маршрута не влияет на чтение, обычную отправку и первичное восстановление.
4. Выбор fallback для новой сессии и переход после сбоя уже начатого хода используют один способ проверки права и квоты, а каждая операция сохраняет своё назначение и собственный ключ. [Техническое восстановление](recovery.md)
