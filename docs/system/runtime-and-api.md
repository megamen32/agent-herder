# Ядро, публичный API и совместимость

## Что система делает сейчас

Rust формирует типизированный каталог из 14 инструментов MCP. Обработчик разбирает действие и различает чтение и запись. `herder_native_stdio` открывает явно заданные профили и может обслуживать несколько экземпляров под одним principal. `herder-http` проверяет идентичность подключения перед вызовом. TypeScript ещё содержит HTTP/Web, каталог совместимости, проекцию старых инструментов и мосты к нативным owner-ам. Наличие действия в схеме определяется отдельно от готовности исполнения у конкретного экземпляра. [Каталог Rust](../../crates/herder/src/mcp/catalog.rs) · [HTTP-граница](../../crates/herder-http/src/lib.rs) · [Multi-owner](../../crates/herder/src/bin/herder_native_stdio/owner_multi.rs) · [Совместимый вход](../../src/index.ts)

## Проблема

Одна команда видна в нескольких API. Без явного владельца поведение зависит от того, какой вход вызвал клиент. При миграции поддержка старого имени может скрывать старый путь записи, а успешный `tools/list` может выглядеть как готовность нативного эффекта.

## Идеальная система

MCP, CLI и Web вызывают общие сценарии приложения. Каждый сценарий умеет адресовать один точный экземпляр, запросить его возможности и вернуть один результат операции. Преобразование старого запроса происходит на входе.

## Идеальный конечный результат

Новый и совместимый клиент выполняют одну операцию в одном чате и получают один нативный результат и одну квитанцию. Добавление адаптера расширяет capabilities через существующий контракт. Остальные входы продолжают работать без отдельных реализаций его политики.

## Анализ по ТРИЗ

Техническое противоречие между обратной совместимостью и единым поведением. Причинная цепочка: новое API копирует старую команду → у каждой копии появляются свои правила авторизации, таймаут и retry → одно действие даёт разные эффекты. Разделение по уровням оставляет различие в кодеке границы и сводит эффекты к одной функции приложения. Дублирующий stateful обработчик можно убрать после доказательства, что совместимая проекция дошла до owner.

## Спецификация

1. Один сценарий приложения принимает команду, проверенную идентичность, снимок состояния и время. Решение о допустимости и переходе чистое. Обработчик эффектов вызывает SQLite и порт конкретного adapter instance. `tools/list` и разбор аргументов строятся из одной схемы.
2. OAuth и trusted stdio устанавливают доверенную идентичность на входе. Поле `sender` используется для атрибуции. Нода-владелец проверяет права на запись и точный session address. Маршрутизация прокси выполняется в [mesh](fleet-routing.md).
3. Доступность нативной операции задаётся по экземпляру. `unsupported`, временная недоступность, отсутствие прав и частичное чтение различимы. Read-only endpoint может быть готов, когда мутация временно недоступна.
4. Совместимые имена и форматы переводятся в общий сценарий, когда для него подтверждён порт. Работающий совместимый writer остаётся владельцем своей возможности до адресного переключения. Обычный клиент получает Task и квитанцию от одного writer-а. [Адаптеры](native-adapters.md) · [Доставка](delivery.md)

## План и приёмка

1. Для каталога составлять связь `действие → entry point → owner → порт → сценарий проверки` по мере изменения функции. Начать с `deliver`, `session.messages`, `automation` и `stop`. Для них самые заметные расхождения UI, Rust и старого API.
2. На [стенде обычного OpenCode-клиента](../../tests/native/ahap_opencode_consumer.py) и в [тестах каталога](../../tests/mcp-catalog-contract.test.ts) сверить одинаковые адрес и ключ, отказ при неверном scope, сохранённую квитанцию после рестарта и различие между заявленной схемой и фактической capability. Совместимое имя считается перенесённым после одного потребительского вызова с тем же результатом.
