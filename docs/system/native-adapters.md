# Нативные харнессы и протокол адаптеров

## Что система делает сейчас

Ядро Rust использует `NativeSessionReader`, `NativeSessionControl` и специализированные порты для создания, Stop и recovery. `herder_native_stdio` открывает экземпляры из профилей. Для Codex и OpenCode код выбирает нативную ветку при наличии нужной привязки; для других конфигураций используется совместимый слой. [Доменный контракт](../../crates/herder/src/domain/adapter.rs) · [Сборка экземпляров](../../crates/herder/src/bin/herder_native_stdio/owner_multi.rs)

| Система | Что подтверждает checkout |
| --- | --- |
| Codex | Чтение и управление app-server из Rust, отдельные порты recovery и goal autopilot. [Код](../../crates/herder/src/adapters/codex) |
| OpenCode | Нативное чтение и управление из Rust плюс существующий AHAP-мост. [Нативный owner](../../crates/herder/src/bin/herder_native_stdio/owner_native_opencode.rs) · [AHAP](../../crates/herder/src/adapters/ahap.rs) |

[Rust](../../crates/herder/src/adapters/zcode) · [Недоставленные вводы](../zcode-undelivered-inputs.md) · [Desktop](../../integrations/zcode-desktop/README.md) |

Наличие исходников или пакета в реестре само по себе подтверждает только реализацию соответствующей точки входа. Серверная готовность и реальный вывод для каждой операции проверяются отдельно.

## Проблема

Похожий текст ошибки может означать недопуск, уже принятую отправку, прерванный ход или нормальное ожидание в разных харнессах. Если в каждом адаптере реализовать ещё и политику retry, цели, очереди и квоты, совпадающие ситуации получат разные эффекты. Если считать все методы обязательными, ограниченный веб-адаптер потеряет даже те операции, которые умеет выполнять.

## Идеальная система

Каждый экземпляр выставляет поддерживаемые операции и переводит родной протокол в общие факты. Один сценарий Rust пользуется этими фактами. Появление второго экземпляра или ещё одного харнесса добавляет профиль и реализацию нужных портов.

## Идеальный конечный результат

Клиент одним способом читает сессии и получает нативные квитанции независимо от харнесса. Поддерживаемая отправка и восстановление работают даже при отсутствии возможности менять модель. Отказ отдельного адаптера виден именно в его capabilities и статусе.

## Анализ по ТРИЗ

Техническое противоречие между общей семантикой и спецификой протоколов. Разделение по уровням: порт извлекает факты из протокола, ядро решает, что с ними делать. Разделение по условию: наличие конкретной capability включает только соответствующее действие. Так убирается повторяющийся policy-код из адаптеров без потери поддержки их нативных возможностей.

## Спецификация

1. Модель чистых данных разделяет идентичность экземпляра, поддержку операции, доступность сейчас и права вызывающего. Ошибки транспорта переводятся в точный outcome, включая `DefinitelyNotSent` и `OutcomeUnknown`. Порты отвечают за чтение и запись по нативному адресу и формат нативной квитанции.
2. Вызов `deliver`, адресный Stop, подтверждение разрешения, recovery и резерв выбираются ядром через соответствующую возможность. Отсутствие порта возвращает `unsupported` для этого действия. Capability резерва проверяется только на стадии резерва. Цели ведёт [автопилот](autopilot.md).
3. Совместимый порт заменяется после сверки поведения для той же операции, сессии и идентичности. Его заменить можно независимо от остальных возможностей харнесса. Установка профиля и переключение writer-а описаны в [выпуске](releases.md).

Для ZCode проверить отдельно активный и холодный сценарии и нативную очередь. [Codex](../../tests/native/codex_recovery_stand.py) · [OpenCode](../../tests/native/opencode_recovery_stand.py) · [ZCode](../../tests/native/v1_zcode_stand.py)
2. На supported-пути проверить один принятый нативный эффект и readback после рестарта; на неподдерживаемом — точный отказ этой возможности, тогда как чтение сохраняется. Без факта расхождения добавлять новые универсальные проверки не требуется.
