# Проекты и рабочие каталоги

## Что система делает сейчас

- В Rust owner-пути OpenCode/AHAP инструмент `discover` с `action=projects` перечисляет только проекты, наблюдавшиеся у разрешённых зарегистрированных сессий. Точное совпадение с native inventory даёт источник `native_project_inventory`, иначе путь публикуется с `authorized_native_session`. Ответ помечен `complete:false` и содержит ограничения. Вложенные наблюдаемые корни сохраняются отдельно. [Каталог MCP](../../crates/herder/src/mcp/catalog.rs) · [Чтение проектов](../../crates/herder/src/bin/herder_native_stdio/owner_reads.rs)
- Для поиска владельца работы `workspace_locate` проверяет каталог на доступных хостах, `workspace_owners` читает текущие заметки и резервации на workspace-хосте. `workspace_status` связывает объявленную рабочую область с неизменным native адресом. Для Git `project_integration` инвентаризирует настоящие worktree, а для release координации они имеют общий Git common dir. Наблюдаемый cwd может быть подкаталогом, а workspace может находиться на другой машине. [Инструменты workspace](../../src/mesh/workspace-tools.ts) · [Инвентаризация Git](../../src/project-worktree-inventory.ts) · [Интеграция проекта](../../src/mcp/project-release-tools.ts)
- Экран «Проекты» редактирует маршруты политики запуска. `POST /api/automation/project-launch` использует диспетчер политики, который выбирает окружение, модель и рабочую область. Проектный fleet create использует сохранённый маршрут, журнал попыток и восстановление scoped adapter по native адресу. Для Codex кандидат отдельного app-server привязан к корню, профилю разрешений и ограничениям инструментов. Для OpenCode предусмотрен маршрут с привязкой попытки и перепроверкой текущего scope. Видимость Rust API ограничивается реестром и текущей политикой владельца. [Экран](../../src/web-ui/projects-settings.tsx) · [Диспетчер](../../src/automation/project-launch-dispatch.ts) · [Runtime интегратора](../../src/integrator-fleet-runtime.ts) · [Политика Codex](../../src/project-runtime-policy.ts) · [ACL владельца](../../crates/herder/src/bin/herder_native_stdio/owner_policy.rs)

Исторический baseline — checkout `fad29a86d944d`; он не подтверждает актуальное состояние всех веток. Метка provenance относится к источнику конкретной строки. Покрытие того среза ограничено зарегистрированными сессиями и доступными наблюдениями. Исходный контракт project scope и кандидат Codex описывают границу допуска. Фактическая файловая и инструментальная изоляция установленного рантайма, его версия и покрытие харнесов здесь не измерялись. Release lease описан в соседней статье и профильном контракте. ## Проблема

Архитектурный риск связан с одной строкой пути для разных решений. Наблюдение cwd помогает найти работу, сохранённый маршрут определяет запуск, канонический корень связывает изоляцию с процессом. Совпадение пути по тексту может скрыть смену хоста, symlink или новую ревизию политики.

## Идеальная система

Поиск объясняет, откуда известен проект и кто объявил работу. Git операции используют реальный worktree. Запуск привязывается к каноническому корню, выбранной машине и ревизии политики. Чтение сессии использует разрешённую запись владельца.

## Идеальный конечный результат

Агент находит точный каталог, владельца работы и подходящий worktree. Запущенная сессия доступна своему владельцу по сохранённой привязке. Подмена корня или потеря подтверждения дают объяснимый отказ в scoped операции. Неполный поиск явно сообщает предел результата.

## Анализ по ТРИЗ

Поиск по cwd даёт совпадения по вложенным путям. Если такое совпадение разрешает запуск или чтение, смена корня либо политики может расширить доступ. Техническое противоречие возникает между удобством поиска и точностью изоляции. Разделение по условию оставляет вложенность для поиска, а исполнение и чтение связывает с подтверждённым корнем и правом на операцию. Польза проверяется сохранением результата по обоим вложенным путям и отказом при изменившемся корне.

## Ресурсы

Реестр сессий и native inventory дают provenance, `git worktree list --porcelain` даёт фактические worktree, а политика запуска и журнал интегратора дают ревизию и привязку к сессии. ## Спецификация

- **Владение состоянием.** Git владеет связью worktree и репозитория. Workspace-хост владеет резервациями путей. Herder хранит политику запуска и привязку попытки. Native owner владеет наблюдением сессии и её доступом.
- **Чистое решение и порты.** Подтверждённые данные определяют кандидатов поиска, точный маршрут запуска и применимость scoped привязки. Git и workspace MCP читают состояние каталогов, runtime owner подтверждает область, adapter выполняет запуск или выдаёт разрешённое чтение.
- **Граница.** Привязка запуска проверяется при допуске у runtime owner по проекту, идентичности корня, ревизии, попытке, хосту и instance. Право просмотра применяет владелец сессии на операции чтения. [Контракт допуска](../../src/project-execution-scope.ts) · [Rust owner reads](../../crates/herder/src/bin/herder_native_stdio/owner_reads.rs)
- **Наблюдаемый результат.** Строки поиска несут источник и полноту. Квитанция запуска связывает проектный корень и нативный адрес. При недействительной привязке scoped операция возвращает отказ.

## План и приёмка

1. Для двух worktree одного Git проекта и вложенного cwd сопоставить фактические checkout, общий ключ release и разные рабочие области. На недоступном хосте поиск возвращает причину.
2. Прочитать проекты разрешённой сессии с точным совпадением native inventory и без него. Проверить оба значения provenance, `complete:false` и отсутствие чужой строки.
3. Сверить проектный запуск и последующее чтение с записью попытки. Для изменившейся ревизии, заменённого корня и чужого principal сверить отказ на соответствующей операции. Изоляцию кандидата подтверждать средствами фактического рантайма по существующему контракту. [Сценарии project scope](../project-execution-scope.md)
