# Планировщик и ожидания Agent Herder

## Что система делает сейчас

**Подтверждено ссылками на текущий checkout; live runtime отмечен отдельно ниже.**

| Путь | Владелец выполнения и сохранения |
| --- | --- |
| Канонический resume_after | При канонической привязке TS переводит запрос в Rust-правило timer или session_completion. Rust-владелец сессии хранит правило, состояние, ревизию и intent в SQLite. Для зависимости фиксируется точный нативный ход, включая ход сессии другого владельца. Ошибка канонической привязки блокирует путь. Поля ожидания ответа человека и его истечения фасад отклоняет. [Выбор](../../src/resume-after-runtime.ts) · [Фасад](../../src/resume-after-canonical.ts) · [Исполнитель](../../crates/herder/src/application/scoped_stop/wait_automation.rs) |
| Legacy resume_after | В legacy-режиме TS-процесс подписывается на нативные события и запускает sweep. Операции сериализованы внутри процесса. Каждое ожидание сохраняется отдельным JSON через временный файл и rename. Dispatching записывается до эффекта. При рестарте читается квитанция по исходному ключу. Здесь есть арбитраж ответа человека и истечения. [Запуск](../../src/index.ts) · [Хранилище и sweep](../../src/resume-after.ts) · [Квитанции](../../src/resume-after-runtime.ts) |
| Cadence | TS-процесс ведёт cadence.json под межпроцессным lock с fsync файла и каталога. До отправки сохраняет dispatching и ключ слота. Sweep берёт только scheduled. Зависший после рестарта dispatching остаётся без автоматического повтора. Шаги — 15 минут в первый час, 30 во второй и затем часовые слоты в :45. Просроченные часовые слоты пропускаются. [Cadence](../../src/cadence-scheduler.ts) · [Адаптация](../../src/cadence-runtime.ts) · [Запуск](../../src/index.ts) |

Cadence и автоматические отправки через SessionSupervisor учитывают process waits. Rust проверяет точный ход зависимости, права, привязки, эпохи HumanStop и карантин миграции. Scoped disarm учитывает каталог и ключ работы. Его читают пути автоматической отправки TS, семантического автопилота Rust и Rust recovery. Покрытие всех вариантов Rust waits общим disarm требует отдельной проверки. Панель отображает состояния владельцев и вызывает их операции управления. ## Проблема

Наступление срока, подтверждение зависимости и запись отправки могут разойтись при рестарте. У TS и Rust разные хранилища и границы допуска. Смешение статуса панели, срока и квитанции затрудняет ответ на вопрос, было ли пробуждение.

## Идеальная система

У каждого ожидания есть один владелец, неизменная идентичность и видимая причина задержки. Часы и доказательства зависимостей открывают допуск. Владелец проверяет запреты перед эффектом, а панель отображает его состояние.

## Идеальный конечный результат

После рестарта ожидание сохраняет срок, зависимости и ключ. У подходящего срабатывания появляется одна квитанция, у отложенного — причина и условие следующей проверки. Всё доступно через существующую панель.

## Анализ по ТРИЗ

- **Цепочка.** Частый sweep сокращает задержку → после медленных чтений накапливаются проверки и претенденты → потеря исходного intent создаёт риск второго пробуждения.
- **Техническое противоречие.** Быстрая реакция ухудшает управляемость повторов. **Разделение по условию.** Для ещё не отправленного правила срок или событие открывает допуск. После начала отправки действует сверка исходного ключа. Для cadence истёкший часовой слот закрывается по политике расписания.
- **Сокращение функции.** Убрать самостоятельный опрос адаптеров и перепланирование из панели и совместимого фасада. Объединять тики при медленном чтении, сохраняя проверку непосредственно перед эффектом.

## Ресурсы

- Из Rust waits подходят точный ход, tombstone, CAS ревизии, проверка циклов и восстановление исходного intent. Из cadence — правила слота и сохраняемый ключ. [Waits](../../crates/herder/src/application/scoped_stop/wait_automation.rs) · [Источники](../../crates/herder/src/application/scoped_stop/wait_sources.rs) · [Cadence](../../src/cadence-scheduler.ts)
- Из outbox подходит раздельная фиксация готовности и исхода. По ключу слота можно искать квитанцию для зависшего cadence, когда адаптер предоставляет такой readback. [Сверка квитанций](../../crates/herder/src/application/scoped_stop/task_reconcile.rs)

## Спецификация

| Слой | Контракт |
| --- | --- |
| Чистое решение | По времени, ревизии, статусу и зависимостям выбрать ожидание, пропуск, отмену, один допуск или сверку квитанции. |
| Наблюдения | Владелец и адрес сессии, исходный ход каждой зависимости, время, занятость, разрешения, waits, HumanStop и применимый disarm. |
| IO | Владелец сохраняет ревизию и ключ перед эффектом. Исполнитель вызывает адаптер. Сверка читает прежнюю квитанцию и сохраняет исход. |
| Обязательные проверки и сбои | Проверять привязки и ревизию, отсутствие цикла, срок и точный ход зависимости. Занятость даёт ожидание или пропуск по правилу. Недоступный источник оставляет статус проверки. Неясная отправка сохраняет ключ для чтения. |
| Избыточные проверки | Полная история при известном ID, вычисление срока в нескольких владельцах, перезапуск отправки при потере ACK. Idle полезен для допуска цели, терминальный исход проверяется по ходу зависимости. |

## План и приёмка

1. Для Rust создать таймер и зависимость, потерять ACK, перезапустить владельца и предъявить другой завершённый ход. Сохраняется прежний intent, повторных отправок нет, ожидание открывается по исходному ходу. Проверить stop-эпоху, CAS и недоступный источник. [Канонические waits](../../crates/herder/tests/canonical_waits.rs)
2. Для cadence проверить границы фаз, занятый часовой слот, pause во время отправки и рестарт в dispatching. Просроченный эффект не догоняется, pause и квитанция сохраняются. [Cadence](../../tests/cadence-scheduler.test.ts)
3. Проверить сбой канонической привязки, отображение недоступного источника и точечный disarm двух соседних работ. [Выбор пути](../../tests/resume-after-production-wiring.test.ts) · [Панель](../../tests/scheduled-tasks-http.test.ts) · [Disarm](../../tests/automation-disarm-chokepoint.test.ts)
