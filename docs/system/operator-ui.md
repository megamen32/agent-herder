# Рабочий кабинет и управление чатом

## Что система делает сейчас

Кабинет показывает локальные и fleet-сессии, активность, модели и историю. Из composer можно создавать сессию, отправлять сообщения, работать с очередью и останавливать чат. В UI есть отдельные поверхности расписаний, разрешений, квоты и настроек. При чтении используются local transcript, fleet observations и проекции совместимости. [Основной Web-клиент](../../src/web-ui/main.tsx) · [Факты сессии](../../src/web-ui/use-session-facts.ts) · [Привязка к fleet-чату](../../src/web-ui/session-detail-identity.ts)

## Проблема

Строка списка, история, composer и статус отправки обновляются с разной частотой и из разных источников. Таймаут может выглядеть как «чат не работает», а текущее `idle` не объясняет, что случилось с последней попыткой. Параллельное правдоподобное состояние размывает различие между HumanStop, окончанием ответа, ошибкой модели и ожиданием очереди.

## Идеальная система

Кабинет запрашивает снимок точной сессии у её owner и показывает только релевантные действия. При открытии видна последняя часть истории. У отправки, восстановления и остановки есть понятная причина состояния и адресная квитанция. Интерфейс отображает решения и доставляет команды владельцу.

## Идеальный конечный результат

Человек открывает один и тот же чат на любой ноде и сразу видит свежие сообщения, модель, последний результат и доступные действия. При `429` он видит ожидание или уже выполненный повтор. Ручное продолжение не требуется для штатного восстановления. Кнопка Stop чётко показывает свой результат.

## Анализ по ТРИЗ

Техническое противоречие между быстрым экраном и согласованными фактами. Цепочка «медленное подтверждение → UI делает локальный вывод → отображается неверное состояние → человек нажимает повтор» разрывается разделением во времени: показать известный снимок с его свежестью и обновить по событию owner. Разделение по уровням убирает локальное принятие решения об автоматическом повторе из UI. Клиент сохраняет состояние представления и черновик.

## Спецификация

1. Владелец состояния действия — соответствующий application owner. Чистая проекция UI принимает snapshot, capabilities и ссылку на Task. Она задаёт отображаемое состояние и доступные действия. Сеть читает owner API и выполняет одно явное действие по стабильному ключу. После потери ответа UI перечитывает ту же задачу.
2. Действия указывают полный session address. Смена выбранного чата отбрасывает запоздалый UI-ответ от прежнего адреса. Загрузка первых 100 сообщений, обновление хвоста и чтение ранних страниц имеют независимые cursor-ы. Capability управляет только своей кнопкой.
3. Отображаемый статус различает временный технический сбой, явный hold, ожидание пользователя, подтверждённый отказ и неизвестный исход. Показывается только причина, относящаяся к текущему адресу и актуальному ходу. Последние наблюдения могут отображаться как устаревшие с их временем.
