# Маршрутизация во флоте

## Что система делает сейчас

- TypeScript MCP регистрирует `mesh_snapshot` и `mesh_discover`. Обход использует настроенных peers через `FleetDirectTransport`; `GptAdminMesh` читает схемы и снимки через переданный транспорт. Веб-кабинет `/api/fleet/*` использует привязанный профиль и транспорт его контура. Вход кабинета проверяет владельца через локальный контур, SSO или настроенный профиль GPTAdmin. Снимок несёт точные native адреса, capability, `launchCwd`, `currentCwd` и источник наблюдения. Лимит окна, отсутствующий источник и недоступный peer отражаются в признаках неполного покрытия. [Композиция MCP](../../src/index.ts) · [Discovery](../../src/mesh/gptadmin.ts) · [Композиция кабинета](../../src/web/fleet-wiring.ts)
- Обычные `deliver` и `send_message` с `target` выбирают локальный или удалённый путь по `target.hostId`. `mesh_route` и `mesh_deliver` доступны старым клиентам. TypeScript проверяет полномочия owner-MCP через метаданные аутентифицированного ingress. Поле `sender` сохраняет атрибуцию. Rust stdio `MultiOwner` выбирает профиль по host и harness, при нескольких кандидатах разрешает точный native ID через реестр. `OwnerPolicy` выдаёт право чтения или записи для principal, instance и членства сессии. - Интегратор использует существующий fleet-путь запуска. `POST /api/fleet/create` входит через кабинет, узловые `fleet_node_info` и `fleet_create_session` публикуют готовность и выполняют проектный create через `IntegratorFleetRuntime`. Контрактная композиция `admitBoundIntegratorSession` покрыта исходными тестами. В ней переход к следующему хосту допускает только явный `not_attempted` с `retryable:true`. ## Проблема

Архитектурный риск возникает при соединении частичного снимка с операцией записи. Устаревший peer может показать сессию, владелец которой уже недоступен. Префикс cwd может найти соседа между workspace, а для доступа к native сессии нужны права на точный адрес.

## Идеальная система

Discovery возвращает происхождение и границы каждого наблюдения. Маршрут использует точный адрес. Владелец принимает решения о доступе и фиксирует исход. Интегратор привязывает запуск к выбранному хосту, маршруту проекта и нативной квитанции создания.

## Идеальный конечный результат

Агенты A и A/B видят разрешённые записи и обмениваются дельтами в обе стороны. Для каждого обращения известны автор, адрес, источник наблюдения и одна квитанция владельца. Частичная недоступность видна в ответе, рабочие peers остаются доступны.

## Анализ по ТРИЗ

При расширении discovery чаще встречаются устаревшие наблюдения и совпадения ID. Если по снимку разрешать запись, запрос может попасть к чужому владельцу. Потеря ответа оставляет отправителя без подтверждения и создаёт риск повтора. Техническое противоречие возникает между широким обзором и точностью допуска. Разделение по уровням оставляет снимку обзор, а owner — действие по точному адресу и ACL. Польза проверяется сохранением доступных строк при падении peer и нулём native вызовов при отказе ACL или неоднозначном адресе.

## Спецификация

- **Владение состоянием.** Владелец сессии хранит её регистрацию, ACL и допуск к эффекту. Workspace-хост хранит резервации путей. Интегратор хранит привязку попытки и исход запуска. Кэш кабинета хранит наблюдения.
- **Чистое решение и порты.** По точному адресу и проверенным наблюдениям выбирается один маршрут или возврат с причиной. Порты чтения собирают peer-снимки, транспорт посылает запрос выбранному owner, native adapter выполняет допущенное действие.
- **Граница.** Право на чтение или запись определяется у владельца для разрешённого principal, instance и сессии. Workspace-префикс группирует наблюдения, а `sender` атрибутирует поручение.
- **Наблюдаемый результат.** Снимок возвращает источник и полноту. Изменение возвращает `inputId` и исход допуска, подтверждённый ход читается с владельца. После UNKNOWN повтор эффекта отсутствует.

## План и приёмка

1. В паре независимых A и A/B прочитать соседей с обеих сторон, затем сверить две направленные дельты с native readback, атрибуцией отправителя и квитанциями. Отдельно сверить одинаковые пути на разных workspace-хостах.
2. При недоступном peer получить частичный снимок с причиной. При неоднозначном адресе или отказе ACL получить отказ до native вызова.
3. В маршруте интегратора сверить проект, корень, хост и native адрес по записи попытки. При потерянном ответе сверить UNKNOWN и отсутствие второго запуска. [Привязка попыток](../integrator-session-binding.md)
