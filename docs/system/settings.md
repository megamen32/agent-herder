# Настройки и управление профилями

## Что система делает сейчас

Rust разбирает ограниченный типизированный `configure.set` для endpoint ноды и экземпляра и модели сессии с revision и необходимой capability. Совместимый Web-контур содержит каталог настроек, product-owned файлы и механизм синхронизации явно общих параметров между выбранными нодами. Он различает записанное и подтверждённое применение. Секреты выводятся только как признак наличия и отпечаток. [Rust configure](../../crates/herder/src/application/settings.rs) · [Каталог](../../src/web/settings-catalog.ts) · [Общие настройки](../../src/common-settings/service.ts) · [Изоляция продуктов](principles-isolation-and-settings.md)

## Проблема

Одно намерение может попасть в переменные окружения, профиль, UI override и унаследованный default. Пользователь видит новое значение, пока запущенный процесс работает со старым. Глобальное распространение добавляет риск изменить экземпляр, который к данной настройке отношения не имеет.

## Идеальная система

По каждому параметру есть один владелец, перечень конкретных областей применения и одна правка из Web или MCP. Результат показывает эффективное значение, источник и когда его прочитает нужный runtime.

## Идеальный конечный результат

Оператор меняет одну настройку один раз, сразу видит затронутые ноды и получает подтверждение применённой ревизии. Пропавший узел сохраняет последнее рабочее значение и досинхронизируется по возвращении. Настройки экземпляров и чужих продуктов сохраняются.

## Анализ по ТРИЗ

Техническое противоречие между единым управлением и изоляцией. Разделение по области: общий default существует только для параметров, назначенных этой группе, а локальная привязка действует по exact scope. Разделение во времени: сохранение и подтверждённое применение показываются отдельно. Дублирующие правки env и UI устраняются, когда оба входа пишут одну версионированную запись.

## Спецификация

1. Запрос явно задаёт параметр, scope и ожидаемую revision. Чистая функция проверяет форму, capability, видимость и необходимость применения. Порт владельца атомарно сохраняет новое значение, а runtime сообщает читаемую ревизию. Случаи конфликта, ожидания рестарта или недоступной ноды возвращаются раздельно.
2. Наследование и override имеют один порядок. Смена настройки действует только на назначенный scope. Secret store владеет секретным значением, публичные DTO содержат только безопасный признак состояния. Включение или отключение каждого writer-а связывается с фактически используемой возможностью.
3. Модельные лимиты принадлежат [политике маршрутов](models-and-routing.md), правила продолжающей автоматики — [автопилоту](autopilot.md) и [планировщику](scheduler.md), параметры browser binding — [экземпляру аккаунта](browser-accounts.md). Форма использует их сценарии и показывает установленное состояние.

## План и приёмка

1. Для каждого меняемого поля проследить `form → API → owner record → runtime effective`. Сначала решить расхождения действующих настроек, способные повлиять на восстановление или браузерный профиль. Переиспользовать `configuration revision` и существующие подтверждения ноды. [Общий сервис](../../src/common-settings/service.ts)
2. Проверить stale revision, локальный override и независимый экземпляр, offline readback после подключения, рестарт и отсутствие секретного значения в ответе.
