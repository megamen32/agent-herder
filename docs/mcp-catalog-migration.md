# Каталог MCP: первый срез L02

Обычный `tools/list` скрывает ровно два внутренних endpoint:
`session_search_local` и `list_active_sessions_local`. Для поиска и активного
инвентаря агенту предлагаются прежние `session_search` и `list_active_sessions`.

Это изменение advertisement. Оба точных локальных имени остаются
зарегистрированы: прямой `tools/call`, штатная валидация аргументов, обработчики,
их отказы и существующие полномочия сохраняются. Скрытие не является запретом
вызова и не предоставляет новых прав. Peer callers не нужно переименовывать.
Доставка, очередь, HumanStop, sync/async и lifecycle сессий не меняются.

## Публичный SDK и реализация

Установлен `@modelcontextprotocol/server` 2.0.0. Публичный
`McpServer.server.setRequestHandler(method, handler)` позволяет зарегистрировать
обработчик протокольного метода. Отдельного advertise-only флага нет;
`RegisteredTool.disable()` запрещает также прямой вызов и здесь не применяется.

`withCatalogProjection` используется только при синхронной начальной регистрации
tools в общей фабрике, до connect. На это время он оборачивает публичный
`setRequestHandler`, сохраняя штатный SDK handler для `tools/list`. Проекция
фильтрует его результат без изменения оставшихся schemas, metadata, порядка
или cursor. Публичный метод регистрации восстанавливается в `finally`.
`tools/call` передаётся SDK без изменений. Приватные поля SDK, внутренний реестр,
конверсия схем и валидаторы не читаются и не заменяются.

Если SDK изменит форму регистрации или не зарегистрирует `tools/list` внутри
этого блока, создание сервера явно завершится ошибкой до подключения. После
обновления SDK повторить catalog-policy и catalog-contract тесты. Это не
механизм подключения к уже работающему серверу и не динамический профиль.

## Проверка и граница доказательств

RED до fix: production factory рекламировала внутренние readers; проверка их
отсутствия падала, а две проверки прямого вызова с неверными аргументами
проходили. GREEN проверяет точную разницу между штатным и проецированным
каталогами одной фабрики, включая неизменность всех оставшихся схем. SDK-тест
проверяет успешные прямые вызовы скрытых endpoint, строгую валидацию до handler
и сохранение отказа handler. Он использует изолированные callbacks и не
является доказательством живой авторизации.

Дополнительная проверка установленного SDK 2.0.0 подтверждает, что
`update({enabled:false})` исключает tool из discovery и отклоняет прямой call,
а `remove()` удаляет его и отклоняет call как not found. Эти факты не
опровергаются проекцией. Отдельный протокольный тест подтверждает: повторный
публичный `setRequestHandler("tools/list", ...)` заменяет предыдущий list
handler, не добавляя второй dispatch, и оставляет штатный tools/call рабочим.
На обеих сторонах регистрации проекции проверяется идентичность callback
tools/call: SDK передаёт ровно один handler и ровно тот же объект достигает
регистрации. Меняется только callback tools/list. Проверки выполняются через
связанный SDK Client/InMemoryTransport, без mock SDK и приватных полей.

Число зарегистрированных tools зависит от конфигурации. В изолированной
тестовой конфигурации наблюдается 73 → 71, а не 87 → 85. Исходный подключённый
каталог в задаче содержит 87; ожидаемый результат после установки при той же
конфигурации — 85. Тестовые числа нельзя выдавать за установленный runtime.

Команда целевых проверок:

```sh
./node_modules/.bin/vitest run --root . --config vitest.config.ts tests/mcp-catalog-policy.test.ts tests/mcp-catalog-contract.test.ts
```

Независимая consumer-проверка после отдельно назначенной установки должна
сохранить полный `tools/list` с пагинацией, runtime revision и профиль клиента;
подтвердить 87 → 85 и отсутствие только этих двух имён; проверить разрешённые
прямые peer вызовы и сохранение существующих отказов. До этого L02 остаётся
running. Этот срез не включает runtime/config/deploy/restart/commit/push.

Дальнейшие этапы 79, 76 и optional 42 здесь не реализованы.
