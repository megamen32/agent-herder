# Нативные сессии MiniMax Code в Herder

## Что это даёт

До этой правки Herder видел нативные сессии MiniMax Code только как локальную
адаптерную строку. В mesh их не было: нативный peer публиковал только Codex, а
локальный mesh отклонял доставку во всё, кроме `codex`. Нативная сессия MiniMax
Code была не адресуемой — до неё не доходили ни резерв путей, ни notes, ни
остановка.

Теперь нативная сессия MiniMax Code — полноценная herder-сессия:

- **Адрес.** `{hostId, harness:"minimax-code", nativeSessionId}` — тот же
  `addressKey`, что и у остальных харнесов. Нативный id одной и той же сессии
  на разных хостах — разные адреса.
- **Публикация.** `mesh_snapshot` нативного peer публикует Codex **и**
  MiniMax Code; недоступность одного источника не отменяет другой, а честно
  отражается в `complete`/`discovery`.
- **Доставка.** `mesh_deliver` в нативную сессию MiniMax Code идёт через
  локальный адаптер (`sendMessage` → `MinimaxCodeControl`) и возвращает
  доказательный приём: `state: admitted` + native `turnId` + тот же `inputId`.
- **Notes.** Доставка несёт активные coordination notes встроенным в сообщение
  блоком `<agent-herder-coordination>` — тот же формат, что у остальных путей.
- **Резерв путей.** Сессия объявляет своё рабочее место через
  `workspace_declare(hostId=…)`; резерв проксируется на хост-владелец, а
  конфликт возвращается ответом и доходит до сессии через доставку выше.
- **Остановка.** `stop_agent` с `hostId` останавливает нативную сессию на
  чужой машине через существующий mesh/peer-транспорт: на целевом хосте
  локальный адаптер вызывает `stopSession` (внутри `MinimaxCodeControl.abort`).
  Сессия останавливается, но **не удаляется** — гашение созрательное.
- **Забор остановки.** Остановка на чужой машине записывает **там же** ручную
  остановку в тот же стор остановок, который пишет локальный путь, и только
  потом гасит сессию. Без этой записи остановленная сессия остаётся открытой
  для автоматических доставок. Повтор той же остановки — одна запись и одно
  гашение; неопределённый исход не переигрывается. Если запись не состоялась
  (у харнеса нет забора), результат говорит об этом прямо: остановлено, но
  забор не записан, автоматические доставки ещё могут дойти.

## Как это включается

1. **На клиентской машине** должен быть запущен MiniMax Code desktop runtime:
   приложение публикует свой loopback-транспорт, манифест которого лежит в
   `~/.minimax/run/mcode-diagnostic.json` (переопределяется
   `MINIMAX_CODE_CONTROL_MANIFEST`). Без опубликованного транспорта сессии
   видны, но доставить в них и остановить их нельзя.
2. **Стор сессий** — `~/.minimax/v2/sessions` (переопределяется
   `MINIMAX_CODE_SESSION_STORE`). Наблюдатель и адаптер читают один и тот же
   стор: `YYYY/MM/DD/<time>-session_<base64url(sessionId)>/manifest.json`.
3. **Herder на этой машине** регистрирует адаптер MiniMax Code, если включён
   `ENABLE_MINIMAX_CODE` (по умолчанию включён). Тогда `mesh_snapshot` и
   `mesh_deliver` локального mesh работают с нативными сессиями.
4. **Нативный peer** (`src/mesh/native-peer.ts`) публикует обе платформы
   наружу. Сборка leaf — та же, что и раньше:
   `NODE_OPTIONS=--max-old-space-size=768 node src/mesh/build-peer.mjs`.
   Новые источники peer добавлены в manifest источников сборки.

## Что именно читается

Наблюдатель (`src/mesh/native-minimax-code.ts`) — **read only**, читает только
метаданные:

- `manifest.json` — native id, `createdAtMs`, `updatedAtMs`, layout, source.
- `snapshot.json` — только префикс до metadata-record (`workspaceDir`, `title`,
  `status`), если стор его держит. Сам файл не читается целиком: транскрипт
  рядом с record не попадает в память.

Наружу не уходит **ни одного** текста сообщения. Title — либо metadata-title
из snapshot, либо синтетическая метка `MiniMax Code session <хвост id>`.
Control-символы вырезаются, title ≤160 символов.

## Ограничения

- **Статус не выдумывается.** Если стор не сообщает статус — сессия остаётся
  видимой, но `status:"unknown"`.
- **Рабочий каталог только из стора.** `currentCwd` публикуется, только если
  стор его подтверждает (`project.source:"native_session_store"`), иначе
  `source:"unverified"`. Для сессий текущей раскладки (`v2-final-dated-session`)
  стор не держит snapshot — каталог и статус остаются неподтверждёнными, и
  Herder не придумывает их.
- **Fail-closed.** Незнание, отказ транспорта и отсутствие доказательства
  приёма — это `not_attempted`/`unknown`, а не «доставлено».
- **Неопределённый приём не переигрывается.** `unknown` остаётся в ledger
  (`harness-mesh-receipts.json`) и повтор с тем же `inputId` не отправляет
  сообщение снова. Повтор допускается только для доказанного
  `not_attempted` с `retryable:true`.
- **Notes в leaf-пути.** Стор notes хаба и стор клиентской машины — разные
  файлы. Notes подставляет хаб: в локальном mesh-пути и в сетевом пути к
  нативной сессии MiniMax Code (`GptAdminMesh.deliver`). Блок тот же
  `<agent-herder-coordination>`, правила те же: повторная инъекция только при
  материальном изменении. Сторона назначения пропускает свою подстановку,
  когда блок уже в сообщении, поэтому двух блоков и повторов одной заметки не
  бывает. Сетевой путь codex не менялся: заметки хаба по-прежнему не идут в
  него. Чтобы заметка хаба попала в доску удалённой сессии, она объявляется с
  `hostId` этой машины.
- **Границы объёма.** Сообщение ≤4000 символов, `inputId` обязателен и
  стабилен, максимум 6 сообщений на пару и 12 на цель за минуту.
- **Никаких удалений.** Herder не удаляет сессии: остановка гасит ход, но
  сама сессия и её история остаются на месте.
- **Рабочее место нужно объявить.** MiniMax Code держит один рабочий каталог на
  весь рантайм, поэтому herder не знает, где работает конкретная сессия. Чтобы
  действовала политика моделей по проектам (и чтобы резерв путей знал, что
  защищать), сессия объявляет своё рабочее место через `workspace_declare` с
  реальным каталогом проекта. Пока рабочее место не объявлено, herder не знает
  проект сессии и не доставляет в неё работу при политике, ограничивающей
  модели.

## Тайм-аут обнаружения

`AGENT_HERDER_MESH_DISCOVERY_TIMEOUT_MS` задаёт общее окно обнаружения локальных
провайдеров, по умолчанию 30000 мс, целое число от 100 до 300000. Все провайдеры
начинают чтение одновременно: зависший ранний адаптер не отнимает окно MiniMax.
Внешний fleet transport даёт этому окну ещё 5000 мс на обмен, aggregator —
ещё 10000 мс. Готовые провайдеры возвращают результат сразу; тайм-аут — максимум,
а не обязательная задержка.
Неверное значение возвращает default с диагностикой в stderr. При изменении
защищённого `~/.config/agent-herder/herder.env` требуется restart Herder.

Это окно discovery, а не срок выполнения задания или ожидания ответа модели.
Истёкшее окно возвращает `native_discovery_deadline`; ошибка самого адаптера —
`native_discovery_failed`. Частичный snapshot остаётся частичным, зависшие
провайдеры не объявляются доступными. Тайм-ауты MCP-клиентов задаются отдельно.

При настройке окна свыше 50000 мс увеличьте timeout MCP-клиента выше
`discovery + 10000 мс`. При default30s цепочка30/35/40s укладывается
в обычный клиентский timeout60s. Настройки на удалённых peers задаются
по месту; больший remote timeout требует согласованного окна на hub.

Поиск всех peers запускается параллельно (не более12), без очереди batches.
Весь `mesh_discover` имеет общее окно `discovery + 20000 мс` (default50s),
поэтому при увеличении env клиенту нужен запас и относительно этого окна.
Готовые peer receipts сохраняются, незавершённые возвращаются как partial.
При store>4096 директорий сначала перечисляются новые dated paths; лимит
сохраняется, самый новый день не вытесняется старыми директориями.
