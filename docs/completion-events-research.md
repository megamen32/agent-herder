# Codex turn completion for a cloud orchestrator

## Baseline (ea7ccfe)

* Session liveness and turn outcome answer different questions. The common statuses are running, idle, needs_input, stopped and error (src/types/common.ts:7). A native completion clears activeTurns and stores nativeLastTurn with turnId, status and optional completedAt (src/adapters/codex-app-server.ts:3397). A later exact read refreshes that record (same file:1904). The active inventory skips idle/unloaded threads and can project running from thread status even after reading a terminal latest turn (src/adapters/codex-active-runtime.ts:54,95). Archive-only observations can display idle or stopped (src/adapters/codex-app-server.ts:1073). Finishing a turn leaves the thread available for another turn.
* The supervisor subscribes to harness events and writes native started/completed/failed receipts (src/session-supervisor.ts:1290,1358 and src/native-turn-receipts.ts:46). Explicit interruption takes an early return at src/session-supervisor.ts:1340. Existing receipts carry a resource URI and source but omit the assistant result and parent; publishing twice increments sequence twice (src/herder-events.ts:114). event_list replays a bounded durable tail, exposes truncation, and supports a URI prefix (src/mcp/control-plane-tools.ts:84). Stop/Autopilot judges whether an opted-in session should continue (same file:143). Cadence, resume_after, human_request and job track schedules, timed wakes, human answers and Herder-owned work respectively (src/mcp/tool-consolidation.ts:70,80,85,90 and src/mcp/human-request-tools.ts:102). None is a general Codex completion subscription.
* The MCP server that registers event_list advertises resources.subscribe and listChanged (src/index.ts:887), forwards resource-updated notifications (src/index.ts:955), and does not declare MCP Tasks there. A separate Rust scoped-stop server enables Tasks (crates/herder/src/application/scoped_stop/mcp_task_server.rs:141). HTTP also offers SSE with Last-Event-ID (src/web/server.ts:3422). Cloud Claude cannot receive those notifications; Tasks support on that client is unverified. chatgpt_wake_await demonstrates the blocking-tool pattern (src/mcp/chatgpt-wake-tools.ts:73).

## Chosen interface

Use the existing process-owned journal. Record one terminal event per Codex thread/turn, including failure or interruption, parent when known, and a bounded assistant excerpt. A waiter and a web status reader share this projection. No autonomous delivery into a supervising thread is necessary.

* Call `session_await({"sessionIds":["<native Codex thread ID>"],"timeoutMs":45000})` for current completion. Save the returned cursor. For the next notification pass `afterSequence` equal to that cursor. Re-call on timeout; retry the original cursor after losing a reply. Maximum timeout is 50000 ms.
* For scheduled catch-up call `event_list({"afterSequence":123,"uriPrefix":"herder://completions/codex/"})`. Advance by the last processed sequence on each page. A truncated cursor requires resynchronizing the watched sessions.
* Point watch_url at `https://<existing Herder web host>/api/sessions/codex/<URL-encoded native thread ID>/status` using the existing web/status access. Read state, outcome, finishedAt, lastAssistantMessage and revision. The body contains no wall-clock heartbeat or global cursor. The revision changes only for that session.

### Watching a newly dispatched task

1. Before dispatch, read `event_list({"limit":1})` and save its **latestSequence** as the baseline. This particular read establishes a start boundary.
2. Dispatch the task. Call `session_await({"sessionIds":["child"],"afterSequence":123,"timeoutMs":45000})`, substituting the saved baseline. A fast completion between dispatch and the wait is replayed.
3. On a terminal reply, process `completion` and checkpoint `cursor` together. On a normal timeout (`completion:null`), use the returned cursor for the next wait. After a lost HTTP/MCP reply, use the last checkpoint. Replay is at-least-once to a consumer; the journal records one terminal event per thread and turn. When `truncated:true`, read each watched thread's current status and establish a new baseline. Intermediate evicted turns may be unrecoverable from this feed.

An example return value is `{"completion":{"sessionId":"child","turnId":"one","state":"finished","outcome":"completed","finishedAt":"2026-05-28T20:26:40.000Z","lastAssistantMessage":"Ready for review"},"cursor":124,"truncated":false}`. A known native parent also appears as `parentThreadId`. The digest is limited to 240 characters and can be null when Codex supplies no assistant text. Native completedAt is preferred; its absence uses observation time. A completed turn with questions reports needs_input, an interrupted turn reports stopped, and a failed turn reports failed, including provider/quota failures. A later turn can run in the same thread.

The GET shares the guard of existing web session reads (src/web/server.ts:1233). Managed public web access uses the signed owner cookie and origin checks (src/web/fleet-wiring.ts:290). The MCP bearer applies to /mcp. Configure the URL watcher with existing web access; use the tool when the watcher cannot supply that access. GET reports unobserved at revision 0 until there is evidence. Both surfaces can recover the latest turn via one native summary read. The scope is native Codex app-server threads visible to this Herder instance. CLI-only archive sessions and cross-host event aggregation are outside this implementation.

### Local acceptance

Baseline MCP discovery lacked session_await. The candidate uses a native Codex notification, the supervisor, the process event journal, tool-only MCP and the existing web server. Focused checks cover completion before and during a wait, duplicate notifications, quota failure, interruption, a cold native summary, timeout, cursor replay after reopening the journal, an unrelated thread leaving the watched body stable, and web access controls. The HTTP transport check exercises a stateless MCP call. MCP capability negotiation in the fixture reported resources.subscribe and resources.listChanged, with no tasks capability. Installed-service and public TLS acceptance require a subsequent deployment.
